# 프론트 코드 작성

## 진입점

이 스킬은 진입점을 지정받아 해당 위치부터 실행한다. 진입점 지정이 없으면 `full`.

| 진입점 | 실행 범위 | 용도 | 파라미터 |
|--------|----------|------|----------|
| `full` | §0 → §1 → §2 → §3 → §4A → §4B | 직접 호출 (기본값) | |
| `from-review` | §2 → §3 → §4A → §4B | 기획 검토 완료 후 구현 착수 | |
| `impl-only` | §3 → §4A | 마무리(§4B)는 실행하지 않음 — 상위 스킬이 직접 처리 | `commit-rule` |

## 0. Git 준비

> git-workflow.mdc "브랜치 준비 절차" 참조
> - branch_type: `feat`
> - creation_timing: `immediate`

## 1. 기획 문서 탐색

1. `/docs`에 존재하는 모든 `@index.md`를 읽어 서비스 전체 목차를 파악한다
2. 사용자 입력과 목차 항목을 매칭한다
   - 계층 구조를 활용한다: "재고 관리 엑셀 일괄 입고" → "재고 관리" 카테고리 → "엑셀 일괄 입고" 항목
3. 후보가 2개 이상이면 `AskQuestion` 툴로 후보 목록을 선택지로 제시하여 사용자에게 확인한다
4. 일치 항목이 없으면 `AskQuestion` 툴로 사용자에게 문서 경로를 직접 요청한다
5. 매칭된 문서를 읽되, 추가 문서는 아래 기준으로 제한한다
   - 상위 문서(개요): 해당 도메인의 상위 문서 1개만 읽는다 (예: `order-management.md`)
   - 공통 정책: 기획 문서 본문에서 직접 링크로 참조하는 공통 문서를 읽는다. 직접 링크가 없더라도 페이지 유형에 해당하는 공통 정책은 읽는다 (리스트 페이지 → `list-conventions.md`, 상세 페이지 → `detail-error.md`)
   - 같은 카테고리의 다른 하위 문서(형제 문서)는 읽지 않는다

## 2. 사전 검토 결과 출력

기획 문서 탐색 완료 후, 코드 작성 전에 아래 형식의 메시지를 사용자에게 출력한다:

```
## 사전 검토 결과

> 읽은 기획 문서: {읽은 문서 경로 목록}
> 인지한 기획 섹션: §1 개요, §2 화면 구성, §3.1 파일 업로드, §3.2 미리보기, ...

### 기획에 없거나 불명확한 내용
- (없음)

### 기획 문서 간 충돌
- (없음)
```

- "인지한 기획 섹션"에 기획 문서의 모든 섹션 제목을 한 줄로 나열한다
- 두 예외 섹션이 모두 비어 있으면 → "사전 검토 통과, 구현을 시작합니다" 보고 후 `AskQuestion` 없이 **자동 진행** 
- 하나라도 내용이 있으면 → `AskQuestion`으로 사용자 확인을 받은 후 진행한다
- 사용자 응답에 따라 기획 문서를 수정한 후 구현을 시작한다
- 기획 사전 검토 및 결과 출력 없이 구현 코드를 작성하는 것은 금지한다

## 3. 기존 공통 코드 탐색

구현 코드를 작성하기 전에 재사용 가능한 공통 코드를 파악한다. 별도 보고서를 출력하지 않고, 탐색 결과를 구현에 바로 반영한다.

### 공통 코드 탐색 대상

AGENTS.md에 "프론트 공통 코드 대상" 섹션이 있으면 해당 경로를 탐색해 코드 작성 시 최우선적으로 사용한다.

### 공통 코드 생성 규칙

구현 중 새로 작성하는 유틸 함수, 훅 등이 도메인에 의존하지 않으면 페이지 로컬이 아닌 위 탐색 대상의 해당 경로에 생성한다.

### 탐색 절차

1. 위 경로의 파일 목록을 조회한다. 파일명만으로 내용을 파악하기 어려운 경우(유틸 함수 등) export 목록까지 확인한다
2. 이번 구현에서 사용할 수 있는 컴포넌트/훅/유틸을 식별한다
3. 후보가 있으면 해당 파일의 export와 타입을 읽어 사용 가능 여부를 확인한다

## 4. 구현

### 4A. TDD 루프

1. **기획 문서 분석** — 요구사항, 상태 흐름, 엣지 케이스 파악
2. **테스트 시나리오 목록 작성** — "기획 조항 → 검증할 것" 형태로 정리. 사용자 행동 기반으로 작성
3. **dev-logs 확인** — `docs/dev-logs`에서 `{오늘 날짜 YYYY-MM-DD}_{페이지명}.md` 파일을 찾아 서버 구현 사항을 참고한다.(특히 프론트 구현 유의사항 섹션에 유의) 오늘 날짜 파일이 없으면 사용자에게 dev-logs 파일을 요청
4. **서버 의존성 확인** — `.cursor/rules/progress-tracking.mdc` "스키마 정의"를 참조하여 `docs/PROGRESS.md`의 서버 컬럼 상태에 따라 분기한다:
   - `done` → 건너뛴다
   - `partially-done` → 하단 구현 보류 섹션에서 서버 대상 미구현 항목을 읽고 프론트 영향을 분류한다:
     - **UI만 가능**: 서버 API 없이도 UI/인터랙션을 구현할 수 있음. 구현하되 실제 API 호출부는 TODO 주석으로 표시
     - **구현 불가**: 서버 API가 없으면 기능 자체가 동작할 수 없음. 해당 기능을 TDD 범위에서 제외
     - 분류 결과를 사용자에게 보고한다. "구현 불가" 항목이 0건이면(전부 "UI만 가능" 또는 해당 없음) → 자동 진행. "구현 불가" 항목이 1건 이상이면 → `AskQuestion`으로 확인받는다
     - "구현 불가"로 전부 제외되어 TDD 범위가 0건이면 → "서버 의존성 미해소로 이번에 구현할 항목이 없습니다" 보고 후 종료
   - `-` → 서버 미구현 상태. `AskQuestion`으로 서버 없이 프론트만 구현할지 확인
   - 같은 PROGRESS.md에서 해당 페이지의 `#### 구현 보류`에 "아키텍처 미확정" 항목이 있으면, 해당 기능을 TDD 범위에서 제외한다
5. **테스트 환경 확인** — vitest 등 없으면 **설치 먼저**
6. **독립 구현 단위 식별** — `commit-rule`이 지정된 경우 해당 지시를 따른다. 없으면 하위 기능별, 탭별, 섹션별 등 독립적으로 동작하는 단위를 나눈다
7. **선행 의존성 처리** — API 연동 코드(API 타입, API 함수, queryOptions) 등 다른 단위에 선행하는 작업을 먼저 수행하고 커밋한다. API 연동이 없는 순수 UI 작업은 건너뛴다. step 4에서 "구현 불가"로 분류된 기능의 API 연동 코드는 작성하지 않는다. "UI만 가능"으로 분류된 기능의 API 함수는 시그니처만 작성하고 body를 TODO로 둔다
8. **단위별 루프** — 식별한 단위마다 아래를 반복한다 (단위가 1개면 1회 실행)
   1. 이 단위의 테스트 코드 작성 (`.test.tsx`)
   2. 이 단위의 구현 코드 작성 — 테스트를 통과시키기 위한 최소 구현
   3. 테스트 실행 — 이 단위 + 기존 테스트 모두 통과할 때까지 반복
   4. 커밋 (§5 커밋 타입 결정 규칙 참조) — 각 단위 완료 직후 즉시 수행한다. 별도 todo 항목으로 분리하지 않는다
9. **정적 분석 병렬 실행** — `tsc --noEmit`과 `eslint .`를 **병렬로 실행**한다
   - **둘 다 통과** → 완료
   - **실패 있음** → 타입 오류부터 수정 → 다시 병렬 실행 (둘 다 통과할 때까지 반복)
10. **타입/린트 커밋** — 9에서 수정한 내용이 있으면 커밋한다. 없으면 건너뛴다

### 4B. 마무리

11. **구현 추적 보고서 출력** — 아래 형식으로 사용자에게 메시지를 출력한다

```
## 구현 추적 보고서: {기능명}

> 기획 문서: {경로}
> 기획 요구사항 수: N건
> 참조한 기획 섹션: §2 화면 구성, §3.1 파일 업로드, §3.2 미리보기, ...

### 기획에 있지만 구현하지 않은 것

| 기획 섹션 | 요구사항 요약 | 대상 | 미구현 사유 |
|-----------|-------------|------|-----------|
| (없음) | | | |
```

- "참조한 기획 섹션"에 기획 문서에서 인지한 모든 섹션 제목을 나열한다
- "기획에 있지만 구현하지 않은 것"이 비어 있으면 → "기획대로 구현 완료" 보고 후 자동 진행
- 비어 있지 않고, 사유가 전부 "서버 미구현 의존성" 또는 "아키텍처 미확정"이면 → 보고만 출력하고 자동 진행 (외부 블로커이므로 사용자 개입 불필요)
- 그 외 사유가 있으면 → 사유를 명시하고 `AskQuestion`으로 사용자 확인을 받는다
- step 4에서 "구현 불가"로 분류된 항목은 미구현 사유 "서버 미구현 의존성"으로 자동 기입한다
- step 4에서 "UI만 가능"으로 분류된 항목은 미구현 사유 "서버 미구현 의존성 — UI 선행 구현 완료, API 연동 대기"로 기입한다
- 보고서를 출력하지 않고 구현을 종료하는 것은 금지한다

12. **PROGRESS.md 갱신** — `.cursor/rules/progress-tracking.mdc` "상태 전이 테이블", "하단 섹션 관리" 규칙에 따라 미구현 0건이면 프론트 컬럼을 `done`으로, 1건 이상이면 `partially-done`으로 갱신하고 미구현 항목을 하단 구현 보류 섹션에 기록한다
13. **문서 커밋** — PROGRESS.md를 커밋한다

## 5. Git 커밋

> 구현 커밋의 `{타입}`: feat/ 브랜치면 `feat:`, fix/ 브랜치면 `fix:`
> fix/ 브랜치일 때: PROGRESS.md 체크포인트를 건너뛴다

### 최소 체크포인트

아래 경계는 반드시 별도 커밋으로 분리한다:

0. **기획 문서 수정** (해당 시에만) — §2 사전 검토에서 기획 문서를 수정한 경우. 기획 수정이 없으면 이 체크포인트를 건너뛴다
   - 커밋: `docs: {기능명} 기획 문서 보완`
1. **API 연동 코드** (해당 시에만) — API 타입, API 함수, queryOptions 파일. §4A-7 선행 의존성 처리 시점에 커밋. API 연동이 없는 순수 UI 작업은 이 체크포인트를 건너뛴다
   - 커밋: `{타입}: {기능명} API 연동 코드 작성`
2. **UI 구현/수정** — 컴포넌트 + 테스트 + 훅 + MSW 핸들러 (TDD이므로 함께 커밋). §4A-8 단위별 루프에서 각 단위 완료 시 커밋
   - 커밋: `{타입}: {기능명} UI 구현`
   - 독립적 하위 기능이 있으면 기능 단위로 분리
     - 예: 탭이 3개인 설정 페이지 → 탭별로 커밋 분리
     - `feat: 센터 정보 탭 구현`, `feat: 운영 시간 탭 구현`
3. **타입 체크 + 린트 통과** (해당 시에만) — `tsc --noEmit` + `eslint` 오류를 모두 수정한 후 한 번에 커밋. 오류가 없으면 이 체크포인트를 건너뛴다
   - 커밋: `chore: {기능명} 타입/Lint 오류 수정`
4. **문서** (해당 시에만) — PROGRESS.md
   - 커밋: `docs: PROGRESS.md {기능명} 프론트 완료 갱신`

## 6. 금지 사항

- 테스트 없이 구현만 먼저 작성하는 것
- 테스트 환경이 없다는 이유로 구현을 먼저 작성하는 것 (환경 설치가 먼저)
- 기획에 없는 내용을 추측으로 구현하는 것
- 테스트 시나리오 목록을 나열하지 않고 바로 코드를 작성하는 것
- 기획이 변경되지 않았는데 테스트를 임의로 수정하는 것
- §3 기존 공통 코드 탐색을 생략하고 구현을 시작하는 것
- 동일 목적의 공통 코드가 있는데 페이지 로컬에 새로 만드는 것 (기존 코드의 인터페이스가 부족하면 확장한다)
- 단위별 루프의 모든 단위를 구현한 후 마지막에 커밋하는 것 — 각 단위 완료 직후 즉시 커밋한다

## 7. 테스트 우선순위

| 우선순위 | 대상 | 방법 |
|---------|------|------|
| 필수 | 공유 훅 (`useListParams`, `useAuth`) | `renderHook` 단위 테스트 |
| 필수 | queryOptions 팩토리 | queryKey/queryFn 단위 테스트 |
| 필수 | 리스트 페이지 흐름, 인증 흐름 | RTL + MSW 통합 테스트 |
| 권장 | 유틸 함수, 순수 로직 함수 | 단위 테스트 |
| 선택 | UI 컴포넌트 (`Button`, `Badge`, `Modal`) | RTL 컴포넌트 테스트 |

## 8. 테스트 파일 배치

테스트 파일은 대상 파일과 같은 폴더에 `.test.ts(x)`로 둔다 (Co-location).
