# 서버 코드 작성

## 진입점

이 스킬은 진입점을 지정받아 해당 위치부터 실행한다. 진입점 지정이 없으면 `full`.

| 진입점 | 실행 범위 | 용도 | 파라미터 |
|--------|----------|------|----------|
| `full` | §0 → §1 → §2 → §3A → §3B | 직접 호출 (기본값) | |
| `from-review` | §2 → §3A → §3B | 기획 검토 완료 후 구현 착수 | |
| `impl-only` | §3A만 | 마무리(§3B)는 실행하지 않음 — 상위 스킬이 직접 처리 | `commit-rule` |

## 0. Git 준비

> git-workflow.mdc "브랜치 준비 절차" 참조
> - branch_type: `feat`
> - creation_timing: `immediate`

## 1. 기획 문서 탐색

1. `/docs`에 존재하는 모든 `@index.md`를 읽어 서비스 전체 목차를 파악한다
2. 사용자 입력과 목차 항목을 매칭한다
   - 계층 구조를 활용한다: "재고 관리 엑셀 일괄 입고" → "재고 관리" 카테고리 → "엑셀 일괄 입고" 항목
3. 후보가 2개 이상이면 `AskQuestion` 툴로 후보 목록을 선택지로 제시하여 사용자에게 확인한다
4. 일치 항목이 없으면 `AskQuestion` 툴로 사용자에게 문서 경로를 직접 요청한다
5. 매칭된 문서를 읽되, 추가 문서는 아래 기준으로 제한한다
   - 상위 문서(개요): 해당 도메인의 상위 문서 1개만 읽는다 (예: `order-management.md`)
   - 공통 정책: 기획 문서 본문에서 직접 링크로 참조하는 공통 문서를 읽는다. 직접 링크가 없더라도 페이지 유형에 해당하는 공통 정책은 읽는다 (리스트 페이지 → `list-conventions.md`, 상세 페이지 → `detail-error.md`)
   - 같은 카테고리의 다른 하위 문서(형제 문서)는 읽지 않는다

## 2. 사전 검토 결과 출력

기획 문서 탐색 완료 후, 코드 작성 전에 아래 형식의 메시지를 사용자에게 출력한다:

```
## 사전 검토 결과

> 읽은 기획 문서: {읽은 문서 경로 목록}
> 인지한 기획 섹션: §1 개요, §2 화면 구성, §3.1 파일 업로드, §3.2 미리보기, ...

### 기획에 없거나 불명확한 내용
- (없음)

### 기획 문서 간 충돌
- (없음)
```

- "인지한 기획 섹션"에 기획 문서의 모든 섹션 제목을 한 줄로 나열한다
- 두 예외 섹션이 모두 비어 있으면 → "사전 검토 통과, 구현을 시작합니다" 보고 후 `AskQuestion` 없이 **자동 진행** 
- 하나라도 내용이 있으면 → `AskQuestion`으로 사용자 확인을 받은 후 진행한다
- 사용자 응답에 따라 기획 문서를 수정한 후 구현을 시작한다
- 기획 사전 검토 및 결과 출력 없이 구현 코드를 작성하는 것은 금지한다

## 3. 구현

### 3A. TDD 루프

1. **기획 문서 분석** — 요구사항, 상태 흐름, 엣지 케이스 파악
1-1. **구현 보류 확인** — PROGRESS.md 하단 `#### 구현 보류`에서 해당 페이지의 "아키텍처 미확정" 항목을 확인한다. 해당 항목이 있으면 관련 기능을 이후 TDD 범위에서 제외한다
2. **테스트 시나리오 목록 작성** — "기획 조항 → 검증할 것" 형태로 정리. 사용자 행동 기반으로 작성
3. **테스트 환경 확인** — vitest, supertest 등 없으면 **설치 먼저**
4. **독립 구현 단위 식별** — `commit-rule`이 지정된 경우 해당 지시를 따른다. 없으면 엔드포인트별, 스키마 등 독립적으로 동작하는 단위를 나눈다
5. **선행 의존성 처리** — 스키마 변경 등 다른 단위에 선행하는 작업을 먼저 수행하고 커밋한다
6. **단위별 루프** — 식별한 단위마다 아래를 반복한다 (단위가 1개면 1회 실행)
   1. 이 단위의 테스트 코드 작성
   2. 이 단위의 구현 코드 작성 — 테스트를 통과시키기 위한 최소 구현
   3. 테스트 실행 — 이 단위 + 기존 테스트 모두 통과할 때까지 반복
   4. 커밋 (§4 커밋 타입 결정 규칙 참조) — 각 단위 완료 직후 즉시 수행한다. 별도 todo 항목으로 분리하지 않는다
7. **정적 분석 병렬 실행** — `tsc --noEmit`과 `eslint .`를 **병렬로 실행**한다
   - **둘 다 통과** → 완료
   - **실패 있음** → 타입 오류부터 수정 → 다시 병렬 실행 (둘 다 통과할 때까지 반복)
8. **타입/린트 커밋** — 7에서 수정한 내용이 있으면 커밋한다. 없으면 건너뛴다

### 3B. 마무리

9. **구현 추적 보고서 출력** — 아래 형식으로 사용자에게 메시지를 출력한다

```
## 구현 추적 보고서: {기능명}

> 기획 문서: {경로}
> 기획 요구사항 수: N건
> 참조한 기획 섹션: §2 화면 구성, §3.1 파일 업로드, §3.2 미리보기, ...

### 기획에 있지만 구현하지 않은 것

| 기획 섹션 | 요구사항 요약 | 대상 | 미구현 사유 |
|-----------|-------------|------|-----------|
| (없음) | | | |
```

- "참조한 기획 섹션"에 기획 문서에서 인지한 모든 섹션 제목을 나열한다
- "기획에 있지만 구현하지 않은 것"이 비어 있으면 → "기획대로 구현 완료" 보고 후 자동 진행
- 비어 있지 않고, 사유가 전부 "서버 미구현 의존성" 또는 "아키텍처 미확정"이면 → 보고만 출력하고 자동 진행 (외부 블로커이므로 사용자 개입 불필요)
- 그 외 사유가 있으면 → 사유를 명시하고 `AskQuestion`으로 사용자 확인을 받는다
- 보고서를 출력하지 않고 구현을 종료하는 것은 금지한다

10. **PROGRESS.md 갱신** — `.cursor/rules/progress-tracking.mdc` "상태 전이 테이블", "하단 섹션 관리" 섹션을 참조한다. 미구현 0건이면 서버 컬럼을 `done`으로, 1건 이상이면 `partially-done`으로 갱신하고 미구현 항목을 하단 구현 보류 섹션에 기록한다
11. **dev-logs 작성** — 아래 템플릿에 따라 `docs/dev-logs/{YYYY-MM-DD}_{페이지명}.md` 작성 (오늘 날짜 사용)
12. **문서 커밋** — PROGRESS.md + dev-logs를 커밋한다

## 4. Git 커밋

> 구현 커밋의 `{타입}`: feat/ 브랜치면 `feat:`, fix/ 브랜치면 `fix:`
> fix/ 브랜치일 때: dev-log, PROGRESS.md 체크포인트를 건너뛴다

### 최소 체크포인트

아래 경계는 반드시 별도 커밋으로 분리한다:

0. **기획 문서 수정** (해당 시에만) — §2 사전 검토에서 기획 문서를 수정한 경우. 기획 수정이 없으면 이 체크포인트를 건너뛴다
   - 커밋: `docs: {기능명} 기획 문서 보완`
1. **스키마 변경** (해당 시에만) — DB 스키마 파일과 drizzle, prisma 등 ORM 마이그레이션 메타 파일 포함. §3-5 선행 의존성 처리 시점에 커밋
   - 커밋: `chore: {기능명} DB 스키마 정의`
2. **API 구현/수정** — 라우트 + 테스트 파일 (TDD이므로 함께 커밋). §3-6 단위별 루프에서 각 단위 완료 시 커밋
   - 커밋: `{타입}: {기능명} 서버 API 구현`
   - 독립적 엔드포인트가 여러 개면 엔드포인트별로 분리
     - 예: `feat: 주문 목록 조회 API 구현`, `feat: 주문 상세 조회 API 구현`
3. **타입 체크 + 린트 통과** (해당 시에만) — `tsc --noEmit` + `eslint` 오류를 모두 수정한 후 한 번에 커밋. 오류가 없으면 이 체크포인트를 건너뛴다
   - 커밋: `chore: {기능명} 타입/Lint 오류 수정`
4. **문서** (해당 시에만) — dev-log, PROGRESS.md
   - 커밋: `docs: {기능명} 서버 구현 문서 작성`

## 5. 금지 사항

- 테스트 없이 구현만 먼저 작성하는 것
- 테스트 환경이 없다는 이유로 구현을 먼저 작성하는 것 (환경 설치가 먼저)
- 기획에 없는 내용을 추측으로 구현하는 것
- 테스트 시나리오 목록을 나열하지 않고 바로 코드를 작성하는 것
- 기획이 변경되지 않았는데 테스트를 임의로 수정하는 것
- 단위별 루프의 모든 단위를 구현한 후 마지막에 커밋하는 것 — 각 단위 완료 직후 즉시 커밋한다

## 6. 테스트 우선순위

| 우선순위 | 대상 | 방법 |
|---------|------|------|
| 필수 | Express 라우트 (`server/src/routes/`) | vitest + supertest. DB는 `vi.mock('../db/client.js')`로 mock |
| 권장 | 유틸 함수, 순수 로직 함수 | 단위 테스트 |

## 7. 테스트 파일 배치

테스트 파일은 대상 파일과 같은 폴더에 `.test.ts(x)`로 둔다 (Co-location).

## 8. dev-logs 작성 템플릿

서버 구현 완료 후 `docs/dev-logs/{YYYY-MM-DD}_{페이지명}.md`에 아래 구조로 작성한다. 오늘 날짜를 사용한다 (예: `2026-05-06_재고-목록.md`). 프론트 구현 시 이 파일을 참조한다.

```markdown
# dev-log: {페이지명}

> 관련 기획 문서: [{기획 문서 제목}]({상대 경로})

---

## 1. API 엔드포인트 요약

| 메서드 | 경로 | 설명 |
|--------|------|------|
| ... | ... | ... |

## 2. 응답 형식

주요 엔드포인트의 응답 JSON 구조와 필드 타입 표

## 3. 요청 파라미터

쿼리/바디 파라미터, 기본값, 허용 값 범위

## 4. 비즈니스 규칙 및 제약

- 서버에서 검증하는 규칙 (프론트에서 중복 검증 또는 UX 반영 필요한 것)
- 권한별 차이 (역할에 따른 403/400 조건 등)

## 5. 프론트 구현 유의사항

- 구현 중 발견한 엣지 케이스
- 기획에 명시되지 않았지만 서버에서 처리한 사항
- 프론트에서 주의할 동작 (정렬 기본값, 상태 전이 조건 등)

### 서버 미구현으로 인한 프론트 제약 (partially-done인 경우만 작성)

| 미구현 서버 기능 | 프론트 영향 | 권장 대응 |
|-----------------|-----------|----------|
| {미구현 API/로직} | {프론트에서 불가능해지는 것} | UI만 선행 구현 / 전체 제외 |

- 서버가 `done`으로 끝나면 이 테이블을 생략한다
- `partially-done`이면 PROGRESS.md 하단 `#### 구현 보류` 항목과 1:1 대응하여 작성 필수
```
