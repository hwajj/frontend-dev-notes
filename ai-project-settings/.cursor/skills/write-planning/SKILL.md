## 1. 문서 구조 개요

```
docs/
├── @index.md              # 전체 목차 (번호 체계의 Single Source of Truth)
├── auth.md               # 공통 문서 (비고 섹션에 등록)
└── order/                # 카테고리 폴더 (하위 문서 2개 이상일 때 생성)
    ├── order-flow.md     # 상위 문서
    ├── product-catalog.md
    └── order-history.md
```

## 2. 문서 연결 규칙

### 공통 규칙

- Single Source of Truth 원칙을 반드시 준수
- 다른 문서를 언급해야 할 때는 요약을 포함한 일체의 내용은 절대 포함해서는 안 되며 반드시 **상대 경로 링크로** 참조할 것
- 링크 생성 시 Markdown 제목을 활용하며, <a> 태그를 별도로 생성하지 않는다.  
- 같은 파일·같은 앵커로 가는 링크는 **본문 곳곳에 반복하지 말고**, 개요 끝 또는 **§2. 화면 구성** 직전 등 **한두 곳**에 모은다. 표·불릿마다 동일 링크를 붙이면 읽기 흐름이 끊긴다.

### 상위 문서

```markdown
# 주문 프로세스

## 하위 문서

- [주문 목록](./order-list.md)
- [주문 상세](./order-detail.md)
```

### 하위 문서

- 문서 최상단에 blockquote로 역참조 링크를 추가한다
  - 독립 하위 페이지 (새 기능): `> 상위 문서: [X](...)`
  - 분리 문서 (기존 페이지 섹션을 별도 파일로 분리): `> 본문: [X](...)`
- `> 본문:` 은 기존 문서에서 내용을 이동할 때만 사용한다 (신규 콘텐츠 작성 시 사용 금지)

```markdown
> 상위 문서: [주문 프로세스](./order-flow.md)

# 상품 목록
```

```markdown
> 본문: [엑셀 일괄 업로드](./delivery-excel-upload.md)

# 템플릿
```

## 3. 각 섹션 작성 지침

### 테이블 포매팅

**열 너비 공백 금지** — 셀 값과 `|` 사이에는 공백을 **반드시 1개**만 넣는다. 열 너비를 맞추기 위한 패딩 공백을 추가하지 않는다.

```markdown
<!-- DON'T: 열 너비 정렬용 공백 -->
| 내부 ID              | UI 한글(초기안) | 책임          |
| -------------------- | --------------- | ------------- |
| `ORDER_SUBMITTED`    | 주문접수        | 요양원        |

<!-- DO: 공백 1개 -->
| 내부 ID | UI 한글(초기안) | 책임 |
|------|------|------|
| `ORDER_SUBMITTED` | 주문접수 | 요양원 |
```

**복수 항목** — 셀에 항목이 **2개 이상** 나열될 때는 `<br>` + `-`로 구분한다. 항목이 1개이면 `-` 없이 평문으로 작성한다.

```markdown
<!-- DON'T: 마침표·쉼표로만 구분 → 읽기 어려움 -->
| 타이머 효과 | 접수 시 타이머 중지. 문제 없음 시 재시작. 배송예외 시 중지 유지. |

<!-- DO: 항목별 줄바꿈 -->
| 타이머 효과 | - 접수 시 타이머 **중지** <br>- "문제 없음" 확인 완료 시 재시작 <br>- "배송예외 등록 예정" 시 중지 유지 |
```

### 섹션별 지침

- **메타**(옵션): 페이지 ID·역할·URL·요구사항 링크
- **개요**: 이 페이지가 어떤 역할을 하는지 요약 서술. 페이지 세부 기능들은 나열하지 않는다.
- **화면 구성**: ASCII 아트로 레이아웃 뼈대를 그리고, **화면 요소** 표(항목·설명)로 개별 요소를 보충. 하나의 행에 정책·합의·링크 등을 과하게 넣지 않고, 내용이 많아지는 경우 별도 섹션으로 분리 서술.
- **기능 상세**: 상태 흐름(**시간 순·조건 순** 서술), 유효성 검사, 권한, 에러 처리 등 동작 규칙을 상세히 서술. 필요한 경우 mermaid flowchart로 기능에 대한 유저 플로우를 작성.
- **TBD**: 미정, VNext에 대한 내용은 **`## TBD`**에 모은다. 상단의 본문에는 현재까지 확정된 사항만 서술(V1, V2, ... 언급 금지)하며 VNext 내용에 대한 서술 없이 TBD 섹션으로의 링크로 대체한다.(ex. "지급 정산 모두 **월 1회** 정산서를 발행한다. 정산 주기 다변화는 [TBD](#tbd)")

## 4. 워크플로우

기획 문서를 작성하거나 수정할 때는 아래 순서를 따른다. 기존 문서 수정 시 **(신규)** 표시된 step은 건너뛴다.

1. `docs/@index.md`를 읽어 현재 목차와 번호 체계를 파악한다
2. **(신규)** 새 문서의 위치(도메인, 상위/하위)를 결정한다. [index-rules.md](./index-rules.md)를 읽고 따른다.
3. **(신규)** index-rules.md의 폴더 생성 규칙에 따라 필요시 폴더를 생성한다
4. 각 섹션 작성 지침에 맞춰 md 파일을 작성·정리한다
  4-1. **(신규)** [document-template.md](./document-template.md)를 읽고 기본 구조에 맞춰 작성한다
5. **(신규)** 하위 문서라면 상단에 상위 문서 역참조 링크를 추가한다
6. **(신규)** 상위 문서에 새 하위 문서 링크를 추가한다
7. **(신규)** @index.md 목차에 새 문서를 추가하고, 필요시 이후 번호를 재정렬한다
8. 수정 파일 수집 — `git diff --name-only -- docs/` 를 실행하여 변경된 기획 문서 목록을 확인한다
9. `docs/PROGRESS.md`를 읽어 각 파일의 현재 서버·프론트 상태를 확인한다
10. `docs/PROGRESS.md` 동기화 — `.cursor/rules/progress-tracking.mdc` "amended 판정", "하단 섹션 관리", "@index.md 동기화", "비고 포맷"의 규칙에 따라 수행한다. 모든 문서 수정 작업이 완료된 후 마지막에 수행한다.
    a. 8에서 수집한 파일 목록을 아래 형식의 분류 테이블로 출력한다
       | 파일 | 구분 | amended | 비고 |
       |------|------|---------|------|
       - 구분: 추가 / 삭제 / 수정 / 수정(전파)
       - amended: 수정·수정(전파)인 경우만 amended 판정 수행. 추가/삭제는 `-`
       - 개요 페이지가 수정된 경우, "amended 판정" 섹션의 개요 페이지 전파 규칙에 따라 영향받는 하위 페이지를 `수정(전파)` 구분으로 추가하고 amended 판정을 수행한다
    b. 분류 테이블에 따라 PROGRESS.md를 갱신한다 (행 추가/삭제, amended 전이, 비고 기록, §2-2 하단 섹션 처리)
