# 구현 검증

구현 에이전트와 **별도 채팅 세션**에서 실행하는 것을 권장한다. 이 스킬은 코드를 수정하지 않는다 — 보고만 한다.

## 1. 기획 문서 탐색

1. `docs/PROGRESS.md`를 읽는다
2. 사용자 입력과 테이블 행의 페이지명을 매칭한다
3. 후보가 2개 이상이면 `AskQuestion` 툴로 확인한다
4. 매칭된 행의 링크에서 기획 문서 경로를 추출하여 읽는다
5. 매칭된 문서 + 아래 관련 문서를 함께 읽는다
   - 상위 문서(개요) 1개
   - 기획 문서 본문에서 직접 링크로 참조하는 공통 문서. 직접 링크가 없더라도 페이지 유형에 해당하는 공통 정책은 읽는다 (리스트 페이지 → `list-conventions.md`, 상세 페이지 → `detail-error.md`)
   - 해당 페이지와 데이터를 주고받는 형제 문서 (예: 목록↔상세)
   - 그 외의 @index.md '공통 문서' 섹션의 문서는 본문에서 참조할 때만 읽는다

## 2. 요구사항 추출

`.cursor/rules/progress-tracking.mdc` "스키마 정의"를 참조하여 PROGRESS.md 상태를 해석한다.
- 매칭된 항목의 서버 또는 프론트 컬럼이 `amended`, `-`(미착수), `reviewed`, `skip` 중 하나인 경우: "구현이 완료되지 않았거나 검증 대상이 아닌 항목입니다. 먼저 `/continue-impl {페이지명}`을 실행하여 구현을 진행해주세요."라고 안내하고 **검증을 즉시 중단한다**.
- 매칭된 항목의 서버/프론트 컬럼이 `partially-done`이면, 해당 항목의 구현 보류 섹션에서 미구현 내역을 읽어 "이미 알려진 미구현(known gap)"으로 분류해둔다. 이 항목들은 §4 교차 대조에서 "미구현"으로 이중 집계하지 않고, §6 보고서에서 별도 섹션으로 표시한다.

기획 문서의 모든 섹션을 읽고, 구현 가능한 요구사항을 번호 목록으로 추출한다.

- 화면 요소 (필드, 버튼, 테이블 컬럼 등)
- 기능 동작 (클릭 시 동작, 상태 전이, 유효성 검증 등)
- 비즈니스 규칙 (권한, 조건 분기, 에러 처리 등)
- 엣지 케이스 (빈 데이터, 경계값, 동시 접근 등)

## 3. 구현 코드 탐색

해당 기능의 구현 파일과 테스트 파일을 찾는다.

- 파일명, import 경로, 라우트 경로 등으로 탐색
- `src/` (프론트엔드)와 `server/src/` (서버) 양쪽을 확인한다
- 테스트 파일(`.test.ts`, `.test.tsx`)도 함께 찾는다

## 4. 교차 대조 (기획 → 코드)

2번에서 추출한 요구사항 하나씩에 대해:

- 해당 요구사항을 구현한 코드가 존재하는가?
- 해당 요구사항을 검증하는 테스트가 존재하는가?
- 코드가 요구사항의 **의도**와 일치하는가? (단순 존재 여부가 아니라 내용 확인)
- 해당 코드가 실행될 때 **대표 입력값의 처리 경로**가 기획 의도와 일치하는가? 기획에서 명시한 주요 입력·조건 1~2개를 골라, 코드상 분기·변환·검증 로직을 따라가며 결과가 기획과 동일한지 확인한다.

## 5. 역방향 대조 (코드 → 기획)

구현 코드에서 기획 문서에 근거가 없는 기능을 찾는다.

- 기획에 언급되지 않은 UI 요소, 버튼, 필터
- 기획에 없는 API 엔드포인트나 파라미터
- 기획 의도와 다르게 동작하는 로직

## 6. 검증 보고서 출력

아래 형식으로 결과를 사용자에게 보고한다.

```
## 검증 보고서: {기능명}

> 기획 문서: {경로}
> 검증 대상 파일: {파일 목록}

### 검증 결과 요약

- 기획 요구사항: N건
- 구현 확인: X건
- 미구현: Y건 (높음 A건 / 보통 B건 / 낮음 C건)
- 기획 외 추가: Z건
- 구현 불일치: W건

### 미구현 항목

| 기획 섹션 | 요구사항 요약 | 대상 | 미구현 사유 |
|-----------|-------------|------|-----------|

### 기획 외 추가 항목

| 구현 위치 | 설명 |
|-----------|------|

### 구현 불일치 (기획과 다르게 구현된 것)

| 기획 섹션 | 요구사항 요약 | 실제 구현 | 구현 위치 | 대상 |
|-----------|-------------|----------|----------|------|

### 기존 미구현 항목 (partially-done에서 인지됨)

| 기획 섹션 | 요구사항 요약 | 대상 | 미구현 사유 |
|-----------|-------------|------|-----------|
```

- "기존 미구현 항목" 섹션은 `partially-done` 항목 검증 시에만 표시한다. §2에서 분류한 known gap을 여기에 기재하고, "미구현 항목" 섹션에서는 제외한다. `partially-done`이 아닌 항목 검증 시 이 섹션은 생략한다
- 각 섹션에 해당 항목이 없으면 "(없음)"으로 표기한다
- 미구현 항목의 `미구현 사유`에는 `구현 누락`을 고정값으로 기입한다
- 미구현 항목의 심각도는 테이블이 아닌 검증 결과 요약 텍스트에 `높음`(핵심 기능 누락) / `보통`(부가 기능 누락) / `낮음`(세부 사항)으로 집계한다
- "구현 불일치"는 단순 누락이 아니라 **기획과 다른 방식으로 구현된 것**을 잡아낸다
- "대상" 컬럼 값: `서버` / `프론트` / `서버+프론트` — **이슈를 수정하려면 어디를 고쳐야 하는가**를 기준으로 판단한다
  - API가 해당 파라미터/필드를 지원하지 않음 → `서버` 또는 `서버+프론트`
  - API는 정상이나 UI에서 해당 데이터를 사용하지 않음 → `프론트`
  - API 응답 형식이 기획과 다름 → `서버`
  - UI 렌더링/동작이 기획과 다름 (API는 정상) → `프론트`
  - 양쪽 모두 변경 필요 → `서버+프론트`

## 7. 기획 외 추가 항목 처리

검증 보고서의 "기획 외 추가 항목"이 1건 이상이면, 각 항목에 대해 `AskQuestion` 툴로 처리 방법을 사용자에게 확인한다.

선택지:
- **기획에 반영** — 해당 기능을 기획 문서의 적절한 섹션에 추가한다. `write-planning` 스킬의 규칙을 따른다.
- **코드에서 제거** — PROGRESS.md 하단 `## 미구현/불일치 항목` 섹션에 "기획 외 제거" 카테고리로 기록한다. continue-impl이 수정 흐름에서 해당 코드를 제거한다.
- **무시** — 별도 조치 없이 넘어간다.

"코드에서 제거"를 선택한 항목이 1건 이상이면, 해당 항목들은 8단계에서 `needs-fix`로 처리한다.

## 8. PROGRESS.md 갱신

검증 보고서 출력 후 `.cursor/rules/progress-tracking.mdc` "상태 전이 테이블", "하단 섹션 관리" 규칙에 따라 `docs/PROGRESS.md`를 갱신한다.

### 8-1. 이슈 없음

조건: 미구현 0건 AND 구현 불일치 0건 AND 코드에서 제거 0건

- 검증 컬럼을 `done`으로 갱신한다
- 서버/프론트 컬럼이 `partially-done`인 경우 그 상태는 유지한다

### 8-2. 이슈 있음

조건: 새로 발견된 미구현 / 구현 불일치 / 코드에서 제거 중 1건 이상

- 검증 컬럼을 `needs-fix`로 갱신한다 (이미 `needs-fix`이면 컬럼 값 유지)
- 최신 검증 결과로 하단 섹션을 새로 기록한다
- 해당 카테고리에 항목이 없으면 해당 섹션을 생략한다 (빈 테이블 금지)
- "기획 외 제거"에는 7단계에서 사용자가 "코드에서 제거"를 선택한 항목만 포함한다

## 9. 금지 사항

- 코드를 수정하는 것 — 이 스킬은 보고 전용이다
- 발견된 문제를 임의로 수정하거나 "사소하므로 무시"하고 생략하는 것
- 사용자 확인 없이 기획 문서를 수정하는 것 (7단계에서 사용자가 "기획에 반영"을 선택한 경우에만 기획 문서 수정 가능)
