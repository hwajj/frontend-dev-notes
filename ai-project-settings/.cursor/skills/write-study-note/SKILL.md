# 세션 학습 노트 작성

[study-notes.mdc](../../rules/study-notes.mdc)의 **결과물 형식·파일 규칙·INDEX 갱신**을 따른다.  
이 스킬은 **학습 대상 범위만 확장**한다 — [categories.md](./categories.md)의 A~D.

**워크플로**: `Plan`(주제 확정) → `Write`(선택분만 **쉽게** 작성) → `Report`

**톤 목표**: 전공 용어·면접 질문을 **몰라도** 태블릿으로 다시 읽으면 이해되는 글. 동료에게 말하듯, 교과서 정의 나열보다 **왜·비유·함정**을 앞에 둔다.

**독립 가독성 목표 (최우선)**: 이 레포를 열어본 적 없고, 당일 세션에 없었던 사람이 **이 md 파일 하나만** 읽고도 이해할 수 있어야 한다. “우리 팀에서 겪은 것”, env 키·포트 번호, 파일 경로는 **개념·흐름을 먼저** 설명한 뒤에만 등장한다.

**설명 순서 목표**: 독자가 “왜 이 프로젝트에서는 증상을 못 봤는지”까지 이해하게 한다. 브라우저·보안·네트워크·프록시 주제는 [개념 설명 순서](#개념-설명-순서-브라우저보안네트워크)를 따른다. 좋은 예: [.study/2026-05-28_cors-vite-dev-proxy.md](../../.study/2026-05-28_cors-vite-dev-proxy.md).

## 1. Plan — 세션 분석·주제 후보

대화·diff·구현·테스트·기획 검토 전체를 훑으며 **노트로 가치 있는 주제 후보**를 뽑는다.

| 소스 | 찾을 것 |
|------|---------|
| 구현·리팩터 | 패턴 선택 이유, 트레이드오프, 팀 규칙과의 접점 |
| 버그·디버깅 | 잘못된 가정, 재현 조건, 회귀 방지 |
| 기획·정책 | 상태 전이, 권한, 사용자 함정 |
| Q&A·설명 | 면접·실무에서 다시 나올 개념 (FE·서버·DB·CS) |

[categories.md](./categories.md) **작성 제외**·study-notes **작성하지 않는 경우**는 후보에서 제외한다.

### 후보 규칙

- **한 후보 = 한 핵심 주제** (파일 1개 또는 기존 파일 섹션 1개에 대응)
- 후보마다 내부 메모: `id`, `제목`, `카테고리`, `한 줄 요약`, `기존 .study 파일 여부`
- 후보 **0건** → Plan 종료, **왜 없는지** 한 줄 보고. **Write 단계 진행 금지**
- 후보 **1~8건** 권장. 9건 이상이면 유사 주제를 묶어 8건 이하로 줄인 뒤 질문한다

### Plan 산출물 (에이전트 메모, 사용자에게도 잠깐 보여줌)

Plan 질문 전에 후보 목록을 표로 정리한다:

```markdown
## 학습 노트 Plan

| # | 카테고리 | 제목(안) | 한 줄 | 비고 |
|---|----------|----------|-------|------|
| 1 | DB·ORM | ... | ... | 신규 파일 |
```

## 2. Plan — 사용자 복수 선택 (필수)

**`.study/`에 파일을 쓰기 전에** 반드시 `AskQuestion`으로 주제를 확정한다.

### AskQuestion 규칙

- `allow_multiple`: **true** (복수 선택)
- 질문 1개. `prompt` 예: `이번 세션에서 .study/에 정리할 주제를 고르세요. (복수 선택 가능)`
- 각 후보를 **선택지 1개**로:
  - `id`: `{주제-kebab}` (영문 소문자·하이픈, 파일명에 사용)
  - `label`: `[{카테고리}] {제목(안)} — {한 줄 요약}` — **전문 용어만 쓰지 말고** 일상어로 (40자 내외)
- 마지막 선택지 **항상** 포함:
  - `id`: `skip-all`
  - `label`: `이번에는 작성하지 않음`

### 응답 처리

| 응답 | 동작 |
|------|------|
| `skip-all`만 선택 또는 아무것도 없음 | Write 생략, "작성 취소" 보고 후 종료 |
| 1개 이상 주제 id 선택 | **선택된 id 순서대로** Write 진행 |
| 후보 1건뿐 | 그래도 AskQuestion 호출 (자동 작성 금지) |

**중요**: 사용자 응답을 받기 전까지 `.study/` 파일 생성·수정·INDEX 갱신 **금지**.

## 3. Write — 선택 주제만 작성

선택된 각 주제에 대해 **한 노트 = 한 파일**(또는 기존 파일 섹션 추가).

### 경로·이름

- 경로: `.study/`
- 신규: `YYYY-MM-DD_{id}.md` (`id`는 AskQuestion에서 쓴 kebab)
- 동일 날짜·유사 주제 파일 있음 → 새 파일 금지, 기존 md에 `## {제목}` 섹션 추가

### 본문 템플릿

study-notes.mdc 골격을 따르되, 아래 **독립 가독성용 머리말**을 **항상** 넣는다. 그 다음 본문(단일 주제면 표준 섹션, 복수 주제면 `## 1. …` 번호 섹션).

```markdown
# {제목}

> 작성일: YYYY-MM-DD
> 맥락: {독자가 겪는 문제·질문 — 세션 일지·“Q&A 정리” 금지}

## 이 글의 질문

{독자가 검색하거나 동료에게 물을 법한 문장 1~3개}

## 핵심 (먼저 읽기)

{선택이 아니라 **권장**. 표 1개로 “이 레포 기본 / 우회 시 / 다른 도구”를 한눈에.  
예: 프록시 쓰면 CORS 안 보임 vs env 직통 vs Postman}

## 전제 (30초)

{등장인물·역할만. 이 레포 이름·브랜치·팀 이슈 없이.}
- 예: 브라우저(화면), 개발 서버(프론트), API 서버(백엔드) — 각각 **무엇을 하는지** 한 줄

## 한눈에

{요청·데이터 흐름. **경로가 2개 이상이면 다이어그램 2개** — 예: “증상 없는 경로(프록시)” / “증상 나는 경로(직통)”.  
포트·경로는 여기서 **처음** 소개하고 라벨 붙인다}

## 용어 (이 글에서만)

| 용어 | 한 줄 뜻 |
|------|----------|
| Origin | … |

---

{아래는 주제당 1세트. 복수 주제면 ## 1. … ## 2. …}

## 한 줄 요약 (또는 정책 한 줄)

## 함정 한 가지

## 왜 이렇게인가

## 참고 코드

## 이 레포에서는 (프로젝트에 대입)

## 더 볼 것 (선택)
```

**주차·회고 글** (`*주차_*.md`): `시리즈 N/M`, 이전/다음 편, `## 면접 한 줄` 섹션 금지. study-notes.mdc 「주차·팀 회고 글」 참고.

**섹션 이름**: `## 프로젝트에 대입` → `## 이 레포에서는` (개념을 다 읽은 뒤 “우리 코드는 여기”라는 뜻이 분명해지도록).

### 독립 가독성 (필수)

**독자 가정**: React·Vite·이 레포를 모른다. 당일 채팅·버그 재현을 보지 않았다.

| 규칙 | 설명 |
|------|------|
| 개념 → 레포 | `CLIENT_ORIGIN`, `VITE_*`, `vite.config.ts`는 **전제·한눈에·용어**로 독자가 그림을 그린 **뒤**에만 등장 |
| 맥락 줄 | 세션 로그(“Q&A로 정리”) 대신 **독자 문제** (“브라우저 콘솔에 CORS가 뜬다”) |
| 번호·포트 | `5173`·`3001` 등은 **한눈에** 다이어그램에 라벨로 한 번 정의. 본문에서 “5174라서”처럼 **전제 없이** 비교 금지 |
| 증상 먼저 | “팀에서만 난다”류는 **증상(콘솔 문구·Network 탭에서 보이는 것)** → **가능한 원인** → **확인 방법** 순 |
| 섹션 입구 | 각 `##`(번호 섹션 포함) **첫 문장**에 “지금 무엇을 설명하는지” 한 줄 (앞 절을 안 읽어도 됨) |
| env·파일 | 첫 등장 시 **역할** 한 줄 (`VITE_API_BASE_URL`: 빌드 시 axios가 붙는 API 주소) |
| 코드 인용 | 경로 인용 블록 **위에** “일반적으로 무엇을 하는 설정인지” 한 줄 → 그다음 “이 레포에서는 …” |

**독립 가독성 실패 예** (피한다):

- `맥락: CLIENT_ORIGIN, VITE_API_BASE_URL을 두고 Q&A 정리` — 키워드만 나열, 문제가 안 보임
- `5174로 접속해도 CORS가 안 난다` — 5174가 뭔지(대체 Vite 포트) 설명 없음
- 표에 `OK 예시 | CORS 나기 쉬운 예시`만 있고, **OK가 무엇을 의미하는지** 문장 없음
- `Postman은 되는데 브라우저만 안 된다`만 쓰고 **URL·Origin·누가 요청 주체인지** 없음 → [도구 비교](#도구-비교-postman-vs-브라우저-등) 위반

### 개념 설명 순서 (브라우저·보안·네트워크)

CORS·쿠키·프록시·캐시·인증 헤더 등 **브라우저 규칙**이 섞인 주제는 본문(번호 섹션)을 아래 순서로 맞춘다. 도메인·React만 다루는 글은 1~2만 적용해도 된다.

| 순서 | 섹션 제목(안) | 쓸 내용 |
|------|----------------|---------|
| 1 | **언제 발생하나** (조건) | “~할 때만” — 체크리스트·표 (예: 브라우저 + JS + cross-origin) |
| 2 | **왜 존재하나** (목적) | 동일 출처·해킹 시나리오 등 **역사·목적**. 서버 방화벽이 아님을 구분 |
| 3 | **도구·경로 비교** | Postman vs 브라우저, 직통 vs 프록시 — [도구 비교](#도구-비교-postman-vs-브라우저-등) |
| 4 | **설정/라우팅을 안 한 경우** | 프록시·상대 URL 없이 절대 URL 직통 등 “증상이 보이는” 구성 |
| 5 | **이 레포에서 증상을 못 본 이유** | 기본 env·vite proxy 등 **우리 기본값이 1~4를 가리는 경우** |
| 6 | **디버깅·팀 이슈** (해당 시) | Network Request URL → env → 실행 순 |

**맥락 줄**에 “이 레포는 프록시 때문에 CORS를 못 느꼈다”처럼 **독자가 헷갈린 지점**을 한 문장으로 박는다.

### 도구 비교 (Postman vs 브라우저 등)

“다른 도구에서는 되는데 브라우저만 안 된다”는 **흔한 질문**이지만, **같은 상황이 아니다**. 아래를 지키지 않으면 쓰지 않는다.

| 규칙 | 설명 |
|------|------|
| 막연한 한 줄 금지 | `Postman은 되는데 브라우저만` **단독 문장 금지** |
| URL을 적는다 | 각 시나리오에 `GET http://host:port/path` 형태로 **전체 URL** |
| Origin·페이지 | 브라우저 시나리오에는 **주소창 Origin** + 가능하면 `Origin:` 헤더 |
| 시나리오 라벨 | `시나리오 A — Postman`, `B — 브라우저 직통`, `C — 브라우저+프록시` |
| 비교 표 | “페이지 Origin 있음 / same-origin 검사 / Request URL” 열을 넣는다 |
| 결론 한 줄 | “HTTP는 같아도 **브라우저는 탭 출처 검사가 추가**된다”처럼 **왜 다른지** |

Postman·curl·서버 간 통신은 **브라우저 JS 규칙 밖**임을 먼저 말한 뒤, 브라우저만의 조건을 붙인다.

### 프로젝트 설정이 증상을 가리는 경우

프록시·MSW·기본 env·상대 API 경로 등으로 **로컬에서 버그·CORS·race가 안 보이는** 경우:

1. `## 핵심`·`> 맥락`에 **“이 레포 기본이면 ~가 안 보이는 게 정상”** 명시  
2. 본문에 **§ 이 레포에서 ~를 못 느낀 이유** (또는 동일 제목) **필수**  
3. 학습용으로 **증상을 보는 설정**(env 직통 등)을 짧게 — 실무 권장은 마지막에 구분

### 쉽게 설명하기 (필수)

study-notes.mdc **작성 원칙**을 따르되, 아래를 **반드시** 지킨다.

| 섹션 | 쓰는 방식 |
|------|-----------|
| 이 글의 질문 | 독자 입장 질문. 세션 참여자만 아는 말 금지 |
| 핵심 (먼저 읽기) | 표로 기본/우회/도구 차이. “이 프로젝트에서 왜 못 느꼈나” 한 줄 |
| 전제 (30초) | 배우 3명(브라우저·프론트 dev·API) 수준. **우리 프로젝트명·폴더 구조 없음** |
| 한눈에 | 경로 2개면 다이어그램 2개. 이후 본문은 이 그림을 **가리키며** 설명 |
| 용어 | 본문에 나올 약어·env·포트 **전부** 표에 선등록 |
| 한 줄 요약 / 정책 한 줄 | **비유·일상어** 한 문장. 용어는 괄호로 짧게만 |
| 함정 한 가지 | “이렇게 생각하기 쉽다 → 실제로는 …” **착각 → 결과** |
| 왜 이렇게인가 | 3~7문장 문장형. 대안 1개와 **왜 안 택했는지** |
| 참고 코드 | 블록 위: (1) 일반 역할 (2) 이 레포에서의 위치 |
| 이 레포에서는 | 표로 파일·env 연결. **앞 절을 읽은 뒤** “우리 설정은 이렇다” |

**Write 직전 체크** (노트마다 **전부** 통과해야 저장):

1. `## 전제`·`## 한눈에`만 읽고도 **누가 누구에게 요청하는지** 그려지는가?
2. `## 용어`에 본문의 env·포트·약어가 **빠짐없이** 있는가?
3. `> 맥락`을 세션 없이 읽어도 **왜 이 글을 찾았는지** 알 수 있는가?
4. 처음 나오는 전문 용어에 **5단어 이내** 풀이 또는 비유가 있는가?
5. `## 왜 이렇게인가`만 읽어도 **이유**가 전달되는가?
6. **레포를 clone하지 않은 사람**이 체크리스트·표만 보고도 재현·확인 단계를 따라갈 수 있는가?
7. (브라우저·CORS·프록시 등) **조건 → 목적 → 도구 비교(URL 적음) → 라우팅 안 한 경우 → 이 레포** 순인가?
8. Postman·브라우저를 비교했다면 **시나리오별 전체 URL**이 있는가? `Postman만 된다` 막연 문장 없는가?
9. 기본 설정으로 증상이 가려지면 **“이 레포에서 ~를 못 느낀 이유”** 절이 있는가?

**피할 것**: API 레퍼런스식 나열, 영문 약어만 있는 문장, 세션 회고·“우리는 ~했다”, 전제 없는 포트·env 나열, **도구 비교 없는** “Postman은 되는데 브라우저만”.

**권장**: 짧은 비유 1개, 비교 **표 1개**, 2문장 이하 단락, 복수 주제면 상단 `## 목차` 링크.

### 작성 원칙 (기타)

- 블로그 톤, bullet만 나열하지 않기
- 참고 코드 2~5블록: `src/`·`server/` 최소 단위
- CS·백엔드: 추상만 쓰지 말고 **이 세션 코드·이슈**에 연결
- `docs/` 인용 시 출처 링크; 구현 커밋과 분리

### 주제별 기존 파일 충돌

선택 주제가 기존 `.study/` 글과 겹치면, 해당 주제 처리 직전에 `AskQuestion` 1회:

- `id` / `label` 예:
  - `append` — 기존 `{파일명}`에 섹션 추가
  - `new-file` — 오늘 날짜 새 파일로 작성
  - `skip-topic` — 이 주제만 건너뜀
