# 인증·인가 서버 관점 (세션 · JWT · OAuth)

## 키워드

- **세션 스토어** — 서버가 세션을 저장(메모리/Redis). 확장 시 공유 저장소 필요.
- **Redis** — 빠른 키-값 저장소. 인증에서는 **세션 공유**, 그 외 **캐시**로도 쓰임(용도를 말해야 함).
- **JWT 검증** — 서명 검증(stateless). 만료·블랙리스트 처리.
- **OAuth 2.0 / OIDC** — 제3자 로그인·위임 인가. Authorization Code + PKCE.
- **Refresh 토큰 회전(rotation)** — 재발급 때 이전 토큰 무효화로 탈취 방어.
- **RBAC** — 역할 기반 인가.

## Redis: 세션 vs 캐시

같은 Redis라도 **목적**이 다르다.

| 용도        | 하는 일                    | 깨지면                                          |
| ----------- | -------------------------- | ----------------------------------------------- |
| 세션 스토어 | `sessionId → 로그인 상태`  | 로그아웃·재로그인, sticky 없이도 서버 확장 가능 |
| 캐시        | 자주 읽는 데이터 사본(TTL) | 원본 DB/API에서 다시 채움(성능↓, 정합성은 원본) |

면접에서 "Redis 씁니다"만 하지 말고 **세션인지 캐시인지**를 구분한다. sticky session은 "같은 사용자를 같은 서버로" 붙여 메모리 세션을 유지하는 우회이고, Redis 공유 스토어가 더 일반적인 확장 패턴이다.

## 면접 포인트

- **Q. 세션 방식이 수평 확장에서 겪는 문제는?**
  → 서버가 여러 대면 세션이 특정 서버에만 있어 불일치. Redis 등 공유 세션 스토어나 sticky session이 필요.
- **Q. Redis를 세션과 캐시에 같이 써도 되나?**
  → 가능하지만 키 네임스페이스·TTL·장애 영향이 다르다. 세션 유실은 로그아웃, 캐시 유실은 느려짐.
- **Q. JWT를 즉시 무효화하기 어려운 이유와 대응은?**
  → stateless라 발급 후 서버가 상태를 안 갖는다. 짧은 만료 + refresh 회전, 필요 시 블랙리스트/버전 클레임으로 보완.
- **Q. OAuth에서 PKCE는 왜 필요한가?**
  → 공개 클라이언트(SPA/모바일)에서 authorization code 탈취를 막기 위해. code_verifier/challenge로 교환을 보호.
