# BFF · API Gateway · 서버 구조 감각

## 키워드

- **Monolith** — 하나의 배포 단위에 여러 도메인이 공존. 단순, 규모가 커지면 배포·확장 단위가 묶임.
- **MSA (Microservices)** — 도메인별 서비스·배포. 프론트는 **여러 API**를 만나기 쉽다.
- **API Gateway** — 외부 진입점. 라우팅, 인증, rate limit, TLS 종료 등을 모음.
- **BFF (Backend for Frontend)** — **특정 클라이언트(웹/모바일)에 맞춘** 백엔드. 화면용 aggregate·포맷 변환.
- **Aggregate** — 여러 서비스 응답을 한 번의 프론트 호출로 합침.

## 개념 정리

### 프론트가 MSA를 직접 두드리면

상품·재고·리뷰·유저 서비스를 각각 호출하면:

- 워터폴·CORS·인증 헤더가 서비스마다 달라짐
- 모바일과 웹이 필요한 필드가 다른데 같은 API를 억지로 씀

**BFF**는 "웹용 서버"를 두어 `/page/home`처럼 **화면 단위로 묶어** 주거나, 웹에 맞는 DTO만 내려준다.

```
브라우저 → BFF(웹) → [ Gateway / 내부 서비스들 ]
           ↗
      모바일 BFF (별도일 수 있음)
```

### API Gateway vs BFF

|      | API Gateway              | BFF                            |
| ---- | ------------------------ | ------------------------------ |
| 초점 | 공통 진입·횡단 관심사    | **클라이언트/채널별** API 모양 |
| 예   | 인증, rate limit, 라우팅 | 홈 피드 조합, 웹 전용 필드     |

실무에서는 Gateway 뒤에 BFF가 있거나, Gateway가 BFF 역할을 일부 겸하기도 한다. 이름은 조직마다 다르다. 중요한 건 **"프론트 전용 조립 계층이 왜 생겼는가"**.

### 비동기 후처리 (한 줄)

업로드 트랜스코딩·메일·알림처럼 **요청-응답 안에 넣기 무거운 일**은 큐/워커로 넘기고, API는 "접수됨"만 돌리는 경우가 많다. (Queue 전용 Day는 없음 — 협업 감각용)

## 면접 포인트

- **Q. BFF가 왜 필요한가?**
  → 클라이언트별로 필요한 데이터가 다르고, 여러 마이크로서비스를 브라우저가 직접 조합하면 지연·복잡도·보안 경계가 나빠진다. 서버에서 한 번 조립한다.
- **Q. API Gateway와 BFF 차이는?**
  → Gateway는 공통 관문, BFF는 특정 UI/채널을 위한 API 계층. 겹칠 수 있지만 목적이 다르다.
- **Q. 모놀리스면 BFF가 없나?**
  → 없어도 된다. 다만 "화면용 facade 모듈"이 서버 안에 있는 것과 비슷한 역할을 한다.

## 목표

- Monolith / MSA를 프론트 협업 관점에서 한 줄로 구분한다.
- BFF·API Gateway의 역할과 "왜 내 API가 이렇게 생겼는지"를 설명한다.
- 무거운 작업이 즉시 응답에 안 실리는 이유를 감각적으로 안다.
