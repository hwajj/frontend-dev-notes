# 실시간 통신 (WebSocket · SSE · 폴링)

## 키워드

- **폴링(Polling)** — 클라이언트가 주기적으로 GET 재요청. 구현 쉬움, 서버 부하·지연 트레이드오프.
- **롱 폴링** — 서버가 변화 생길 때까지 응답 보류.
- **SSE (Server-Sent Events)** — 서버 → 클라이언트 단방향 스트림(`EventSource`). 알림에 적합.
- **WebSocket** — 양방향 지속 연결. 채팅·협업 등 실시간 상호작용에 적합.
- **선택 기준** — 단방향 알림이면 SSE/폴링, 양방향이면 WebSocket.
- **GraphQL** — 클라이언트가 필요한 필드를 질의. over/under-fetching 완화. REST와 **대체재이지 만능이 아님**.

## REST 외 통신 한눈에

| 방식        | 방향            | 감각                                                      |
| ----------- | --------------- | --------------------------------------------------------- |
| REST + 폴링 | 요청→응답 반복  | 구현 단순, 실시간성은 약함                                |
| SSE         | 서버→클라       | 알림·진행률 스트림                                        |
| WebSocket   | 양방향          | 채팅·협업                                                 |
| GraphQL     | 요청→응답(질의) | 화면별 필드 조합, 스키마·캐시 복잡도↑                     |
| gRPC        | 주로 서비스 간  | 브라우저보다 백엔드·모바일 네이티브. 알아두면 협업에 도움 |

GraphQL을 쓰는 이유: 모바일/웹이 다른 필드를 원할 때, BFF(→ 11-4) 없이도 클라이언트 주도로 맞출 수 있다. 쓰지 않는 이유: 캐시·N+1·권한·파일 업로드 등 운영 이슈가 REST와 다르다.

## 면접 포인트

- **Q. 폴링 vs WebSocket, 뭘 언제 쓰나?**
  → 알림처럼 "가끔 갱신"이면 조건부 폴링이 구현·운영이 단순. "실시간 양방향"이면 WebSocket. 무조건 WS가 정답은 아니다.
- **Q. React Query로 실시간처럼 보이게 하려면?**
  → `refetchInterval`(조건부 폴링) 또는 이벤트 수신 시 `invalidateQueries`. 폴링+알림 invalidate 조합이 실무에서 흔하다.
- **Q. 폴링의 단점과 완화는?**
  → 불필요한 요청·지연. 백오프, 탭 비활성 시 중단(visibility), 조건부(enabled) 폴링으로 완화.
- **Q. GraphQL은 REST를 대체하나?**
  → 필드를 클라이언트가 고르는 장점이 있지만, 모든 API에 필수는 아니다. 팀 스키마·캐시·관찰 비용과 함께 선택한다.
