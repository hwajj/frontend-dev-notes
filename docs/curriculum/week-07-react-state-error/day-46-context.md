# Day 46: Context

## 키워드

- **Context API** — 컴포넌트 트리에서 props를 여러 단계로 전달하지 않고 값을 공유하기 위한 React 기능.
- **Provider / Consumer** — `Provider`가 공유할 값을 제공하고, 하위 컴포넌트가 `useContext`로 값을 읽는다.
- **Props Drilling** — 부모에서 자식으로 같은 props를 여러 단계 전달해야 하는 문제. Context가 이를 줄여준다.
- **Context의 사용 범위** — 전역적으로 공유할 필요가 있는 값이나 특정 트리 범위에서 공통으로 사용하는 값에 적합.
- **Context와 상태 관리** — Context는 주로 **값을 전달하는 메커니즘**이고, 복잡한 상태 변경·캐싱·서버 상태 관리까지 해결하는 도구는 아니다.
- **Context 리렌더링** — Provider의 `value`가 변경되면 해당 Context를 사용하는 컴포넌트가 리렌더링될 수 있으므로, 불필요한 객체 재생성에 주의해야 한다.

## 질문 예시

- **Q. Context API는 왜 사용하는가?**
  → 컴포넌트 트리 깊숙한 곳까지 props를 반복해서 전달하는 **Props Drilling을 줄이기 위해** 사용한다. 테마, 인증 사용자 정보, 언어 설정처럼 여러 컴포넌트에서 공통으로 사용하는 값을 공유할 때 적합하다.

- **Q. Context API와 Redux/Zustand의 차이는?**
  → Context는 기본적으로 **값을 하위 컴포넌트에 전달하는 기능**이다. Redux나 Zustand는 상태 변경 로직, 상태 구독, 업데이트 구조 등을 제공하는 **상태 관리 라이브러리**다. Context만으로도 간단한 전역 상태를 관리할 수 있지만, 상태가 복잡해지면 별도의 상태 관리 도구가 더 적합할 수 있다.

- **Q. Context를 사용하면 전역 상태 관리가 모두 해결되는가?**
  → 아니다. Context는 상태를 저장하는 것 자체보다 **컴포넌트 간 값을 공유하는 문제를 해결하는 기능**에 가깝다. 특히 빈번하게 변경되는 큰 상태를 하나의 Context에서 관리하면 리렌더링 범위가 커질 수 있다.

- **Q. Context 사용 시 리렌더링 성능 문제는 왜 발생하는가?**
  → Provider의 `value`가 변경되면 해당 Context를 사용하는 컴포넌트들이 업데이트 대상이 된다. 특히 `value={{ user, setUser }}`처럼 매 렌더링마다 새로운 객체를 생성하면 실제 값이 같더라도 참조가 달라질 수 있다. 필요한 경우 `useMemo` 등을 활용해 참조 변경을 줄일 수 있다.

- **Q. Context를 언제 사용하는 게 좋은가?**
  → 여러 컴포넌트에서 공통으로 사용하는 **변경 빈도가 높지 않은 값**에 적합하다. 예를 들어 테마, 로그인 사용자 정보, 언어 설정 등이 대표적이다. 단순히 부모-자식 간 데이터를 전달하는 상황이라면 Context보다 props가 더 명확하다.

- Props Drilling과 Context의 관계를 설명할 수 있다.
- **Context와 Redux/Zustand의 차이**를 설명할 수 있다.
