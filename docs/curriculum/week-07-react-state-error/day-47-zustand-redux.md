# Day 47: Zustand / Redux

## 키워드

- **Zustand** — 간단한 API로 전역 상태를 관리하는 경량 상태 관리 라이브러리. Store를 만들고 필요한 컴포넌트에서 상태를 직접 구독한다.
- **Redux** — 중앙 Store에서 애플리케이션 상태를 관리하고, `action → dispatch → reducer → state` 흐름을 통해 상태를 변경하는 상태 관리 라이브러리.
- **Store** — 여러 컴포넌트에서 공유하는 상태를 보관하는 공간.
- **Action** — Redux에서 상태 변경 의도를 표현하는 객체. Zustand에서는 보통 Store 내부의 함수가 이 역할을 한다.
- **Reducer** — Redux에서 `action`을 받아 새로운 상태를 계산하는 순수 함수.
- **Selector** — Store에서 필요한 상태만 선택해서 구독하는 방식. 불필요한 리렌더링을 줄이는 데 중요하다.
- **Immutable update** — 기존 상태를 직접 변경하지 않고 새로운 상태를 만들어 업데이트하는 방식.
- **Zustand vs Redux** — Zustand는 보일러플레이트가 적고 사용법이 단순한 반면, Redux는 명확한 상태 변경 흐름과 미들웨어·DevTools·규칙 기반 구조가 강점이다.

## 질문 예시

- **Q. Zustand와 Redux의 가장 큰 차이는?**
  → 상태 변경 구조와 사용 복잡성이다. Redux는 `dispatch → action → reducer → state`라는 명확한 단방향 흐름을 따르는 반면, Zustand는 Store에 상태와 업데이트 함수를 정의하고 필요한 컴포넌트에서 직접 구독하는 방식이라 코드가 간결하다.

- **Q. Redux에서 상태를 직접 수정하면 안 되는 이유는?**
  → Redux는 상태 변경을 예측 가능하게 관리하기 위해 불변 업데이트를 기본으로 한다. 기존 객체를 직접 변경하면 변경 감지나 디버깅 과정에서 문제가 발생할 수 있다. Redux Toolkit을 사용하면 Immer를 통해 불변 업데이트 코드를 더 간결하게 작성할 수 있다.

- **Q. Zustand에서 Selector를 사용하는 이유는?**
  → Store 전체가 아니라 **컴포넌트가 실제로 필요한 상태만 구독하기 위해서**다. 필요한 상태만 선택하면 다른 상태가 변경됐을 때 해당 컴포넌트가 불필요하게 리렌더링되는 것을 줄일 수 있다.

- **Q. Context API가 있는데 Zustand나 Redux를 사용하는 이유는?**
  → Context도 공유 상태를 만들 수 있지만, 상태가 많아지고 변경이 빈번해지면 Provider 구조와 리렌더링 관리가 복잡해질 수 있다. Zustand나 Redux는 상태 구독과 업데이트를 보다 체계적으로 관리하기 위한 기능을 제공한다.

- **Q. Redux를 사용하면 모든 상태를 Redux Store에 넣어야 하나?**
  → 아니다. **공유가 필요한 전역 상태만** Store에서 관리하는 것이 좋다. 컴포넌트 내부에서만 사용하는 모달 열림 여부나 input 값 같은 상태는 `useState`로 관리하는 것이 더 적절하다.

- **Q. 전역 상태 관리와 서버 상태 관리는 어떻게 다른가?**
  → Zustand나 Redux는 주로 **클라이언트 상태**를 관리한다. 반면 API에서 받아온 데이터처럼 서버가 원본을 가지고 있는 상태는 React Query 같은 서버 상태 관리 도구가 적합하다. 모든 데이터를 전역 Store에 넣는 것은 좋은 설계가 아니다.
