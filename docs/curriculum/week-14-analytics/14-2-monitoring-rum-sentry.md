# 프론트 관측 (모니터링 · RUM · Sentry)

## 키워드

- **RUM (Real User Monitoring)** — 실제 사용자 환경의 성능 지표 수집(Web Vitals 필드 데이터).
- **에러 모니터링(Sentry)** — 런타임 에러·스택 추적·소스맵 연동.
- **Source Map** — minify/번들된 코드를 원본 파일·라인으로 복원. 배포 시 업로드(또는 비공개 보관).
- **Minified stack** — `a.b()` 한 줄짜리 스택. 소스맵 없으면 원인 추적이 거의 불가.
- **알럿/샘플링** — 임계 초과 시 알림, 트래픽 대비 샘플링.
- **랩 vs 필드** — Lighthouse(랩) vs RUM(실사용). 둘을 함께 봐야 한다.
- **Chrome DevTools** — Network(캐시·워터폴), Performance(롱태스크), Memory(누수 후보).

## 디버깅 감각

| 도구                | 보는 것                                              |
| ------------------- | ---------------------------------------------------- |
| Network             | 상태코드, 304, `(disk cache)`, CORS, 워터폴          |
| Performance         | 롱 태스크, 렌더·스크립트 구간                        |
| Memory              | 힙 스냅샷 비교로 분리자(detach) DOM·리스너 누수 후보 |
| Sentry + Source Map | 사용자 환경의 원본 스택                              |

프로덕션 에러는 거의 항상 minify된다. **소스맵 파이프라인**이 관측의 전제다.

## 면접 포인트

- **Q. Lighthouse 점수는 좋은데 실사용이 느린 이유는?**
  → 랩(고정 환경) vs 필드(다양한 기기·망) 차이. RUM으로 실제 분포(p75)를 봐야 진짜 문제를 잡는다.
- **Q. Sentry에서 압축된 스택이 안 읽힐 때는?**
  → 소스맵 미업로드. 배포 파이프라인에서 소스맵을 함께 올려야 원본 위치로 복원된다.
- **Q. 에러가 너무 많이 잡힐 때는?**
  → 샘플링·그룹핑·무시 규칙으로 노이즈를 줄이고 중요한 이슈에 집중.
- **Q. "메모리 누수"를 프론트에서 어떻게 의하나?**
  → 재현 경로를 반복하며 Memory 힙을 비교. 이벤트 리스너·구독·타이머 미해제가 흔하다.

## 목표

- RUM으로 실사용 Web Vitals(p75)를 측정한다.
- Sentry + 소스맵으로 minified 에러를 원본 기준으로 추적한다.
- DevTools Network/Performance/Memory로 로컬 진단을 보완한다.
- 랩/필드 데이터를 함께 해석해 우선순위를 정한다.
