# Day 6: 인증/저장소

## 키워드

- **Cookie** — 요청 시(조건에 맞으면) 자동 전송되는 작은 데이터. `HttpOnly`, `Secure`, `SameSite`가 보안의 핵심.
- **SessionStorage** — 탭(또는 세션) 단위 키-값. 탭을 닫으면 사라진다. 탭마다 분리.
- **LocalStorage** — 오리진 단위 영속 키-값. 용량·동기 API·XSS 시 JS로 읽힐 수 있음.
- **IndexedDB** — 대용량·구조화 데이터용 비동기 DB. 오프라인·캐시 스토어에 적합.
- **JWT / Session / Token** — 인증 수단의 이름. **어디에 둘지**는 이 Day의 저장소 선택과 Day 26 인증 설계가 만난다.

## 개념 정리

### 언제 뭘 쓰나 (선택 기준)

| 저장소 | 수명·범위 | 자동 전송 | 대략 용량 | 잘 맞는 용도 |
|--------|-----------|-----------|-----------|--------------|
| Cookie | 만료·도메인·경로로 제어 | HTTP 요청에 자동 | 작음(~4KB) | 세션 ID, 선호 언어 등 **서버가 매 요청에 알아야 할 값** |
| SessionStorage | 탭 세션 | 없음 | ~5MB | 마법사 폼 임시값, 탭 한정 UI 상태 |
| LocalStorage | 영속(명시 삭제까지) | 없음 | ~5MB | 테마, 최근 검색어 등 **비민감** 설정 |
| IndexedDB | 영속 | 없음 | 큼 | 오프라인 큐, 대량 목록 캐시 |

### 인증 토큰을 둘 때

- **HttpOnly 쿠키**: JS가 못 읽어 XSS로 토큰 탈취가 상대적으로 어렵다. 대신 쿠키 자동 전송 → **CSRF** 대비(`SameSite`, CSRF 토큰)가 필요하다. (→ Day 26, 09-4)
- **LocalStorage**: 구현은 쉽지만 XSS에 토큰이 노출된다. SPA에서 자주 쓰이지만 트레이드오프를 말해야 한다.
- **SessionStorage**: 탭 단위라 공유가 안 되어 "다른 탭 로그인 동기화"가 어렵다.

JWT·Refresh 흐름의 세부(Access/Refresh, 만료)는 **Day 26**에서 다룬다. 이 Day는 **"어디에 저장하는가"**에 집중한다.

## 면접 포인트

- **Q. Cookie와 LocalStorage 차이는?**
  → Cookie는(조건 충족 시) 요청에 실려 서버로 가고, LocalStorage는 JS가 읽어 API에 직접 붙여야 한다. 용량·보안 속성·자동 전송 여부가 다르다.
- **Q. 로그인 토큰을 LocalStorage에 두면 왜 위험한가?**
  → XSS가 나면 스크립트가 `localStorage`를 읽어 토큰을 훔친다. HttpOnly 쿠키는 JS 접근이 막혀 상대적으로 안전하다.
- **Q. SessionStorage를 쓰는 이유는?**
  → 탭을 닫으면 사라지고 탭 간 공유가 안 되어, **그 탭에서만** 필요한 임시 상태를 두기 좋다.
- **Q. IndexedDB는 언제 쓰나?**
  → 수 MB 이상·구조화 데이터·오프라인 저장이 필요할 때. 설정 한두 개는 LocalStorage로 충분한 경우가 많다.

## 목표

- Cookie / SessionStorage / LocalStorage / IndexedDB를 수명·전송·용량 기준으로 비교한다.
- 인증 값 저장 위치의 보안 트레이드오프를 Day 26·09-4와 연결해 설명한다.
- "임시 UI 상태 vs 서버 인증 vs 대용량 캐시"에 맞는 저장소를 고를 수 있다.
