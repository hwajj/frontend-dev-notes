기존 내용에 면접에서 자주 이어지는 **DNS → TCP/TLS → HTTP → 브라우저 렌더링 → 캐싱 → 쿠키/세션**까지 연결해서, 이후 프론트엔드 면접 질문으로 확장하기 좋은 형태로 정리하면 이렇게 가는 게 좋다.

# Day 1: HTTP 기초

## 키워드

- **HTTP / HTTPS** — 클라이언트와 서버가 데이터를 주고받기 위한 애플리케이션 계층 프로토콜. HTTPS는 HTTP에 TLS 암호화를 적용한 것.
- **Request / Response** — 클라이언트가 서버에 요청을 보내고, 서버가 그 결과를 응답하는 기본 통신 구조.
- **HTTP Method** — `GET`, `POST`, `PUT`, `PATCH`, `DELETE` 등 요청의 목적을 나타낸다.
- **URL** — 서버의 리소스를 식별하는 주소. `scheme`, `host`, `port`, `path`, `query` 등의 요소로 구성된다.
- **Header** — 요청이나 응답에 대한 부가 정보를 전달한다. `Content-Type`, `Authorization`, `Cache-Control`, `Cookie` 등이 대표적이다.
- **Body** — 요청 또는 응답에서 실제 데이터를 전달하는 영역. 주로 `POST`, `PUT`, `PATCH` 등에서 사용한다.
- **Status Code** — 서버가 요청 처리 결과를 나타내는 코드.
  - `2xx` 성공
  - `3xx` 리다이렉션
  - `4xx` 클라이언트 오류
  - `5xx` 서버 오류
- **DNS** — 도메인 이름을 실제 서버의 IP 주소로 변환한다.
- **TCP / TLS** — HTTP 통신 전에 연결을 설정하고 HTTPS에서는 TLS를 통해 통신 내용을 암호화한다.
- **HTTP/1.1 / HTTP/2 / HTTP/3** — HTTP 버전에 따라 연결과 데이터 전송 방식이 달라진다. HTTP/2는 멀티플렉싱, HTTP/3는 QUIC 기반 전송이 핵심이다.
- **Stateless** — HTTP 자체는 각 요청을 독립적으로 처리하는 무상태 프로토콜이다. 로그인 상태 같은 정보를 유지하기 위해 Cookie, Session, Token 등을 활용한다.
- **Cookie** — 브라우저에 저장되는 작은 데이터로, 요청 시 서버에 자동으로 전송할 수 있다.
- **Cache** — 이전에 받은 리소스를 재사용해 네트워크 요청과 로딩 시간을 줄이는 메커니즘.
- **CORS** — 브라우저의 동일 출처 정책으로 인해 다른 Origin의 리소스에 접근할 때 적용되는 보안 정책.
- **Origin** — `scheme + host + port`의 조합. CORS를 이해하기 위한 핵심 개념.
- **브라우저 렌더링** — HTML/CSS/JS를 받아 DOM과 CSSOM을 만들고 렌더 트리를 구성한 뒤 화면에 그리는 과정.
- **Critical Rendering Path** — 브라우저가 HTML, CSS, JS를 처리해 화면을 표시하기까지의 주요 렌더링 과정.
- **Script Loading** — 일반적인 `<script>`는 HTML 파싱을 중단시킬 수 있으며, `defer`와 `async`를 사용하면 로딩과 실행 방식을 조절할 수 있다.

## 질문 예시

- **Q. 브라우저 주소창에 URL을 입력하면 무슨 일이 일어나는가?** → 먼저 URL을 분석하고 DNS서버를 통해 도메인의 IP 주소를 확인한다. 이후 서버와 연결을 수립하고, HTTPS라면 TLS 핸드셰이크(https> 서버가 인증서 여기>브라우저가 암호화에 사용할 비밀키 정하고 키로 데이터 암호화해서 주고받기로함) 를 수행한다. 그 다음 브라우저가 HTTP Request를 보내고 서버가 Response를 반환한다. 브라우저는 받은 HTML을 파싱해 DOM을 만들고 CSS를 파싱해 CSSOM을 만든다. 필요한 JS와 이미지 등의 리소스를 추가로 요청하고, 렌더 트리를 구성해 레이아웃과 페인트를 거쳐 화면에 표시한다.
- **Q. HTTP와 HTTPS의 차이는?**
  → HTTPS는 HTTP를 TLS 위에서 사용하는 방식이다. 데이터를 암호화해 **도청과 변조를 방지**하고, 인증서를 통해 서버의 신원을 확인할 수 있다.
- **Q. HTTP는 왜 Stateless라고 하는가?**
  → HTTP 자체는 이전 요청의 상태를 서버가 자동으로 기억하지 않기 때문이다. 로그인 상태처럼 요청 간 정보를 유지해야 하는 경우 Cookie, Session, Token 등의 별도 메커니즘을 사용한다.

```
 **Cookie** → 브라우저에 저장되는 작은 데이터. 서버가 `Set-Cookie`로 내려주면 브라우저가 이후 요청에 자동으로 함께 보냄. **로그인 상태, 사용자 설정 등에 사용**
- **Session** → 로그인 정보 같은 상태를 **서버에 저장**하고, 브라우저에는 보통 **Session ID를 쿠키로 저장**. 요청이 오면 서버가 ID로 사용자를 확인
- **Token** → 로그인 성공 후 서버가 발급한 문자열. 클라이언트가 저장해두고 요청할 때 함께 보내면 서버가 **토큰을 확인해서 사용자 인증**
- **localStorage** → 브라우저에 데이터를 저장. **직접 삭제하기 전까지 유지**되며 요청할 때 자동으로 서버에 전송되지는 않음
- **sessionStorage** → 브라우저에 데이터를 저장하지만 **해당 탭을 닫으면 삭제**됨. 이것도 자동으로 서버에 전송되지 않음
```

- **Q. GET과 POST의 차이는?**
  → 일반적으로 GET은 리소스를 조회하기 위한 요청이고 POST는 데이터를 서버에 전달해 새로운 리소스를 생성하거나 특정 작업을 수행하기 위한 요청이다. GET은 URL에 query parameter를 포함할 수 있고, POST는 주로 request body에 데이터를 전달한다.
- **Q. PUT과 PATCH의 차이는?**
  → PUT은 리소스 전체를 대체하는 의미로 사용하고, PATCH는 리소스의 **일부를 수정**하는 의미로 사용한다. 예를 들어 사용자 정보에서 이름만 변경한다면 PATCH가 적절하다.
- **Q. HTTP Status Code에서 401과 403의 차이는?**
  → `401 Unauthorized`는 인증 정보가 없거나 유효하지 않아 인증이 필요한 상황이고, `403 Forbidden`은 인증은 되었지만 해당 리소스에 접근할 권한이 없는 상황을 의미한다.
- **Q. 301과 302는 무엇인가?**
  → 둘 다 리다이렉션 응답이다. `301`은 영구적으로 URL이 변경되었음을 의미하고, `302`는 임시적인 이동을 의미한다.
- **Q. 브라우저에서 CORS 에러가 발생하는 이유는?**
  → 브라우저의 **동일 출처 정책(Same-Origin Policy)** 때문이다. 요청 대상의 Origin이 현재 페이지와 다를 경우 서버가 허용한 Origin인지 확인하고, 필요한 CORS 응답 헤더가 없으면 브라우저가 응답 접근을 차단한다.
- **Q. CORS는 서버의 보안 기능인가?**
  → 정확히는 **브라우저가 적용하는 보안 정책**이다. 서버가 CORS 응답 헤더를 통해 어떤 출처의 브라우저 요청을 허용할지 알려주고, 브라우저가 이를 검사한다. 서버 간 통신에는 브라우저의 CORS 정책이 적용되지 않는다.
- **Q. HTTP Header와 Body의 차이는?**
  → Header는 요청이나 응답의 **메타데이터와 제어 정보**를 전달하고, Body는 실제 전달하려는 데이터를 담는다. 예를 들어 `Content-Type: application/json`은 Header에, JSON 데이터 자체는 Body에 들어간다.
- **Q.** `Content-Type`**은 무엇인가?**
  → HTTP Body에 담긴 데이터의 형식을 나타낸다. 예를 들어 JSON 데이터를 전송할 경우 `application/json`을 사용한다.
- **Q. Cookie는 왜 사용하는가?**
  → HTTP가 Stateless이기 때문에 요청 간 상태를 유지하기 위한 방법 중 하나다. 로그인 세션 식별자, 사용자 설정 등의 정보를 저장하고 이후 요청에 함께 전송할 수 있다.
- **Q.** `Cache-Control`**은 무엇인가?**
  → 브라우저나 중간 캐시가 HTTP 응답을 **얼마 동안, 어떤 방식으로 캐시할지** 제어하는 Header다. 캐시를 적절하게 사용하면 동일한 리소스를 매번 서버에서 받아오는 것을 줄일 수 있다.
- **Q. 브라우저에서** `<script>`**가 렌더링에 어떤 영향을 주는가?**
  → 일반적인 `<script>`는 HTML 파싱을 중단하고 JS를 다운로드·실행한 뒤 다시 HTML 파싱을 진행한다. 따라서 큰 JS 파일이나 실행 시간이 긴 스크립트는 초기 렌더링을 지연시킬 수 있다.
- **Q.** `async`**와** `defer`**의 차이는?**
  → 둘 다 HTML 파싱과 동시에 스크립트를 다운로드할 수 있다. `async`는 다운로드가 끝나는 즉시 실행되므로 HTML 파싱과 실행 순서를 보장하지 않는다. `defer`는 HTML 파싱이 끝난 후 실행되며 선언된 순서를 유지한다. 따라서 서로 의존하는 스크립트에는 일반적으로 `defer`가 적합하다.
- **Q. CSS와 JavaScript가 렌더링에 영향을 주는 이유는?**
  → CSS는 화면의 스타일과 레이아웃을 결정하기 때문에 브라우저가 CSSOM을 구성해야 렌더링을 제대로 진행할 수 있다. JavaScript는 DOM과 CSSOM을 변경할 수 있기 때문에 HTML 파싱이나 렌더링 과정에 영향을 줄 수 있다.
- **Q. HTTP/1.1과 HTTP/2의 주요 차이는?**
  → HTTP/1.1은 기본적으로 하나의 연결에서 요청이 순차적으로 처리되는 구조의 한계가 있었고, HTTP/2는 **멀티플렉싱**을 통해 하나의 TCP 연결에서 여러 요청과 응답을 동시에 처리할 수 있다. 또한 Header Compression과 Binary Framing 등을 제공한다.
- **Q. 프론트엔드 개발자가 HTTP를 알아야 하는 이유는?**
  → 프론트엔드는 단순히 UI를 만드는 것이 아니라 브라우저와 서버 사이에서 API를 호출하고 데이터를 주고받기 때문이다. **Request/Response, 상태 코드, 캐시, 인증, CORS, 네트워크 성능**을 이해해야 API 오류와 성능 문제를 제대로 분석할 수 있다.
