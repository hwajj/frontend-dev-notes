# Day 5: 캐시 & 리소스 힌트

## 키워드

- **Memory Cache / Disk Cache** — 브라우저 캐시 계층. Memory는 탭·프로세스 단위로 빠르고, Disk는 재방문에도 남을 수 있다. DevTools Network의 Size 컬럼에서 `(memory cache)` / `(disk cache)`로 구분한다.
- **Cache-Control** — 응답이 얼마나·어떻게 캐시될지 지시. `max-age`, `no-cache`, `no-store`, `immutable` 등이 핵심.
- **ETag** — 리소스 버전 식별자. 재검증 시 `If-None-Match`와 짝을 이룬다.
- **304 Not Modified** — 본문 없이 "그대로 써도 된다"는 응답. 전송량을 줄인다.
- **preload / prefetch** — preload는 현재 페이지에서 곧 쓸 자원 우선 로드, prefetch는 다음에 쓸 가능성 있는 자원을 유휴 시 미리 받기.

## 개념 정리

### 브라우저가 캐시를 쓰는 이유

같은 URL의 JS/CSS/이미지를 매번 전부 받으면 느리고 비싸다. 브라우저는 **이미 받은 복사본**이 유효하면 네트워크를 생략하거나, 서버에 "바뀌었나?"만 물어본다.

### Cache-Control 읽기

| 지시어             | 의미 (실무 감각)                                |
| ------------------ | ----------------------------------------------- |
| `max-age=31536000` | 이 초 동안은 fresh로 보고 재요청 없이 사용 가능 |
| `no-cache`         | 쓰기 전에 서버에 재검증(조건부 요청) 필요       |
| `no-store`         | 캐시에 넣지 않음(민감 응답)                     |
| `immutable`        | 내용이 안 바뀐다고 가정(해시 파일명과 자주 쌍)  |

파일명에 콘텐츠 해시(`app.abc123.js`)를 넣고 `max-age`를 길게 + `immutable`을 주면, **배포 시 파일명이 바뀌며** 자연스럽게 새 자산을 받는다.

### ETag → 304 흐름

1. 첫 응답에 `ETag: "v1"` (또는 약한 검증자)가 온다.
2. 재요청 때 브라우저가 `If-None-Match: "v1"`을 붙인다.
3. 서버가 같으면 **304** (본문 없음), 다르면 200 + 새 본문.

## 면접 포인트

- **Q. Memory Cache와 Disk Cache 차이는?**
  → Memory는 같은 세션/프로세스에서 매우 빠른 재사용, Disk는 디스크에 남아 재방문에도 쓸 수 있다. 둘 다 "브라우저 캐시"이고, CDN·서버 캐시와는 계층이 다르다.
- **Q. `no-cache`와 `no-store`의 차이는?**
  → `no-store`는 저장 자체를 막고, `no-cache`는 저장은 가능하되 사용 전 재검증이 필요하다.
- **Q. 해시 파일명 + 장기 캐시를 쓰는 이유는?**
  → 내용이 바뀌면 URL이 바뀌어 캐시 무효화가 자동이다. HTML만 짧게 캐시하고 자산은 길게 두는 패턴이 흔하다.
- **Q. 304는 성공인가?**
  → 본문은 없지만 "캐시된 표현을 그대로 써라"는 **성공적 재검증**이다. 네트워크 왕복은 있을 수 있어도 바디 전송은 없다.
