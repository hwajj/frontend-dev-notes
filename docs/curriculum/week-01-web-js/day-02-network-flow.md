# Day 2: 네트워크 연결 흐름

## 키워드

- **URL** — 브라우저가 접근할 리소스를 식별하는 주소. `scheme`, `host`, `port`, `path`, `query` 등으로 구성된다.
- **DNS Lookup** — `example.com` 같은 도메인 이름을 서버의 IP 주소로 변환하는 과정.
- **DNS Cache** — 매번 DNS 서버에 질의하지 않도록 브라우저, OS, 라우터, DNS 서버 등이 조회 결과를 일정 시간 저장한다.
- **TCP 3-way Handshake** — TCP 연결을 수립하기 위한 `SYN → SYN-ACK → ACK` 과정.
- **TLS Handshake** — HTTPS 통신에서 서버 인증서를 확인하고 암호화 통신을 위한 키를 협상하는 과정.
- **HTTP Request** — 연결이 수립된 후 브라우저가 서버에 보내는 요청.
- **HTTP Response** — 서버가 요청을 처리한 후 브라우저에 반환하는 응답.
- **IP / Port** — IP는 통신 대상 호스트를 식별하고, Port는 해당 호스트의 특정 네트워크 서비스를 식별한다.
- **Connection Reuse** — 한 번 맺은 연결을 재사용해 매 요청마다 연결을 새로 만드는 비용을 줄인다.
- **HTTP/2 / HTTP/3** — HTTP/2는 TCP 기반 멀티플렉싱을 사용하고, HTTP/3는 QUIC을 기반으로 동작한다.
- **브라우저 렌더링** — HTTP 응답으로 받은 HTML을 파싱하고 CSS, JS 등의 리소스를 처리한 후 실제 화면을 그리는 과정.

## 질문 예시

- **Q. 브라우저에 `https://example.com`을 입력하면 어떤 일이 일어나는가?**
  → 먼저 URL을 분석한다. 브라우저와 OS 등의 캐시에 DNS 정보가 없다면 DNS 조회를 통해 도메인의 IP 주소를 얻는다. 이후 서버와 TCP 연결을 수립하고, HTTPS라면 TLS Handshake를 수행한다. 연결이 준비되면 HTTP Request를 서버에 보내고 Response를 받는다. 브라우저는 HTML을 파싱하면서 필요한 CSS, JavaScript, 이미지 등의 리소스를 추가로 요청하고 렌더링 과정을 거쳐 화면을 표시한다.

- **Q. DNS는 왜 필요한가?**
  → 사람이 기억하기 쉬운 도메인 이름과 실제 네트워크 통신에 사용하는 IP 주소를 연결하기 위해 필요하다. 사용자가 `google.com`을 입력해도 실제 통신에서는 해당 서버의 IP 주소를 알아야 한다.

- **Q. DNS Lookup은 항상 외부 DNS 서버에 요청하는가?**
  → 아니다. 브라우저 캐시, OS DNS 캐시 등에 결과가 남아 있다면 외부 DNS 조회 없이 사용할 수 있다. 캐시에 없다면 설정된 DNS Resolver를 통해 조회하게 된다.

- **Q. TCP 3-way Handshake는 왜 필요한가?**
  → 클라이언트와 서버가 서로 통신할 준비가 되었는지 확인하고 **TCP 연결을 수립하기 위해** 사용한다. 일반적으로 `SYN → SYN-ACK → ACK` 순서로 진행된다.

- **Q. TCP와 UDP의 차이는?**
  → TCP는 연결을 수립하고 데이터의 순서와 전달을 보장하는 신뢰성 중심의 프로토콜이다. UDP는 연결 설정이나 전달 보장 없이 데이터를 보내 상대적으로 오버헤드가 적다. HTTP/3는 UDP 기반의 QUIC을 사용해 TCP의 일부 한계를 보완한다.

- **Q. HTTPS에서는 TCP 연결만 하면 바로 HTTP 요청을 보내는가?**
  → 아니다. HTTPS에서는 TCP 연결 이후 **TLS Handshake**가 필요하다. 이 과정에서 서버 인증서를 검증하고 암호화 통신을 위한 키를 협상한 후 HTTP 데이터를 암호화해서 주고받는다.

- **Q. TLS Handshake에서 인증서는 왜 필요한가?**
  → 접속한 서버가 정말 해당 도메인의 서버인지 확인하기 위해서다. 브라우저는 인증서의 유효성과 신뢰 체인을 확인해 서버의 신원을 검증한다.

- **Q. TCP와 TLS의 역할은 어떻게 다른가?**
  → TCP는 **신뢰성 있는 데이터 전송과 연결 관리**를 담당하고, TLS는 그 연결 위에서 **암호화, 무결성, 서버 인증**을 제공한다.

- **Q. DNS → TCP → TLS → HTTP 순서로 진행되는 이유는?**
  → HTTP 데이터를 보내려면 먼저 통신할 서버를 찾아야 하고(DNS), 서버와 연결을 만들어야 하며(TCP), HTTPS라면 암호화 통신을 위한 보안 연결을 먼저 구성해야 한다(TLS). 그 다음 실제 애플리케이션 데이터인 HTTP를 전송한다.

- **Q. URL의 `https://`, `example.com`, `:443`, `/users`는 각각 무엇인가?**
  → `https`는 Scheme, `example.com`은 Host, `443`은 Port, `/users`는 Path다. HTTPS의 기본 포트는 443이므로 URL에 명시하지 않아도 기본적으로 443을 사용한다.

- **Q. DNS 조회나 TCP 연결을 매번 새로 해야 하는가?**
  → 반드시 그렇지는 않다. DNS 결과는 캐시될 수 있고, HTTP 연결도 Keep-Alive나 HTTP/2 등의 연결 재사용을 통해 기존 연결을 활용할 수 있다. 이를 통해 네트워크 연결에 필요한 비용을 줄일 수 있다.

- **Q. HTTP/2에서는 TCP 연결을 하나만 사용하는가?**
  → 일반적으로 하나의 TCP 연결에서 여러 HTTP 요청과 응답을 **멀티플렉싱**할 수 있다. HTTP/1.1에서 여러 리소스를 처리하기 위해 여러 연결을 사용하는 방식보다 효율적으로 통신할 수 있다.

- **Q. HTTP/3는 HTTP/2와 무엇이 다른가?**
  → HTTP/2가 TCP 위에서 동작하는 것과 달리 HTTP/3는 **QUIC이라는 UDP 기반 전송 프로토콜** 위에서 동작한다. QUIC은 연결 설정 과정과 스트림 처리를 개선해 TCP의 Head-of-Line Blocking 문제를 완화한다.

- **Q. URL 입력부터 화면이 표시되는 과정을 네트워크 관점에서 설명해보라.**
  →
  **URL 입력 → DNS 조회 → TCP 연결 → TLS Handshake → HTTP Request → HTTP Response → HTML 파싱 → 추가 리소스 요청 → CSS/JS 처리 → 렌더링**

  여기서 중요한 것은 **네트워크 통신이 끝난 뒤에야 렌더링이 시작되는 것이 아니라는 점**이다. HTML을 받기 시작하면 브라우저는 이를 파싱하면서 필요한 리소스를 발견하고 병렬적으로 추가 요청을 진행한다.

## 목표

- URL 입력부터 화면 표시까지의 과정을 **DNS → TCP → TLS → HTTP → 렌더링** 순서로 설명할 수 있다.
- DNS가 필요한 이유와 **DNS Cache가 연결 속도에 미치는 영향**을 설명할 수 있다.
- TCP 3-way Handshake의 목적과 과정을 설명할 수 있다.
- TCP와 TLS의 **역할 차이**를 설명할 수 있다.
- HTTPS에서 TLS Handshake가 필요한 이유를 설명할 수 있다.
- URL의 **Scheme / Host / Port / Path**를 구분할 수 있다.
- HTTP/1.1, HTTP/2, HTTP/3의 차이를 기본적인 네트워크 흐름 관점에서 설명할 수 있다.
- **"DNS가 끝나고 TCP가 끝나고 TLS가 끝난 다음에야 화면이 뜬다"가 아니라**, HTML을 받는 즉시 브라우저가 파싱과 추가 리소스 요청을 진행한다는 점을 이해한다.
