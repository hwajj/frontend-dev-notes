# Day 75: 프로젝트 회고 ①

## 키워드

- **프로젝트 회고** — 무엇을 만들었는지보다 **왜 그 결정이었는지**를 언어화.
- **Feature 기반 구조** — 도메인/기능 폴더로 응집(라우트·API·UI를 기능 단위로).
- **공용 컴포넌트 경계** — design system/ui는 재사용, feature 전용은 끌어올리지 않기.
- **Composition** — props·children·slots로 동작을 조합. 상속보다 조립(React 기본 감각).
- **Layered / FSD 감각** — 계층(shared → entities → features → pages)을 **엄격 교리**가 아니라 "의존 방향"으로 이해.

## 프론트 아키텍처 메모 (회고에 쓰기)

면접·회고에서 폴더 나열보다 아래를 말한다.

1. **경계** — 이 모듈은 공용인가, 이 화면에만 필요한가?
2. **의존 방향** — feature가 shared를 보지, shared가 feature를 import하지 않기.
3. **상태 위치** — 서버 상태(RQ) / URL 상태 / 클라이언트 UI 상태(→ Day 37, 08-2, 7주).
4. **실패 경험** — 공용 폴더에 feature 로직이 섞여 생긴 커플링을 어떻게 풀었는지.

Atomic·FSD는 **이름 암기**보다 "의존이 한 방향으로 흐르게, 화면이 기능을 조립한다"는 Composition 설명이 설득력 있다.

## 면접 포인트

- **Q. 폴더 구조를 어떻게 잡았나?**
  → 기능(Feature) 단위로 응집하고, 진짜 공용만 `shared`/`ui`로 올렸다. 초기에 pages 기준으로만 나누면 같은 API·폼이 복제되기 쉽다.
- **Q. 공용 컴포넌트가 비대해지면?**
  → variant가 도메인 분기를 먹기 시작한다. feature 전용으로 내리고, 공용은 시각·접근성만 남긴다.
- **Q. 설계 패턴을 쓰나?**
  → Observer/PubSub는 이벤트·스토어, Adapter는 외부 SDK 래핑처럼 **문제에서 이름을 붙인다**. 패턴 목록을 외워 적용하지 않는다.

## 목표

- 최근 프로젝트의 폴더·상태·공용 경계를 3분 안에 설명할 수 있다.
- Composition·의존 방향으로 "왜 이렇게 나눴는지"를 회고 문장으로 남긴다.
- Day 76에서 장애·성능 회고로 이어갈 재료를 고른다.
