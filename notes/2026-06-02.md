### 장바구니

카탈로그의 +/-는 아직 주문이 확정되지 않았으므로 화면 상태만 바꾼다.
그래서 +를 10번 눌러도 서버 요청은 발생하지 않는다.
사용자가 "담기"를 누르는 순간에만 서버에 저장한다.
즉, "담기"가 임시 상태와 실제 주문 상태의 경계다.
담긴 후 주문서에서 수량을 바꾸면 실제 주문 데이터가 바뀌므로 서버에도 바로 반영한다.
사용자 경험을 위해 화면은 먼저 바꾸고(optimistic update), 서버 응답이 실패하면 원래 값으로 되돌린다.
로컬 상태(React state)는 임시 메모장 역할이다.
Zustand는 앱 전체에서 공유되는 장바구니 역할이다.
서버의 draft API는 최종 기준 데이터(SSOT) 역할이다.

"담기 전에는 화면에서만 관리하고, 담은 후부터는 서버가 관리한다."



### 큰 테이블 리렌더 — state 하나 바뀌면 왜 모든 행이 다시 그려지나
React는 state가 바뀌면 해당 컴포넌트를 다시 실행한다.
부모 컴포넌트가 다시 실행되면 기본적으로 자식들도 같이 다시 실행된다.
그래서 테이블의 한 행 수량만 바꿔도 테이블 전체가 다시 계산될 수 있다.
화면(DOM)이 실제로 안 바뀌어도 React는 비교(diff) 작업을 수행한다.
행이 20개면 괜찮지만 100개, 1000개가 되면 성능 차이가 커진다.
items.map(...)으로 행을 직접 그리면 모든 행이 다시 계산되기 쉽다.
행을 별도 컴포넌트로 분리하고 React.memo를 사용하면 바뀐 행만 다시 그릴 수 있다.
Zustand도 전체 store를 구독하면 불필요한 리렌더가 발생할 수 있어서 필요한 값만 selector로 구독하는 게 좋다.
상태(state)는 가능한 실제 사용하는 컴포넌트 가까이에 두는 것이 성능에 유리하다.

"React는 기본적으로 넉넉하게 다시 그리므로, 큰 리스트에서는 React.memo, selector, state 분리로 리렌더 범위를 줄인다."


### Zustand selector — useStore()를 호출하는 두 가지 방법
Zustand는 전역 상태 저장소다.
useCartStore()는 스토어 전체를 구독한다.
그래서 내가 lines만 써도 다른 값이 바뀌면 컴포넌트가 다시 렌더된다.
useCartStore(s => s.lines)는 lines만 구독한다.
따라서 다른 상태가 바뀌어도 리렌더를 막을 수 있다.
큰 화면이나 큰 테이블에서는 이런 불필요한 리렌더가 성능에 영향을 준다.
Zustand를 사용할 때는 필요한 값만 selector로 가져오는 것이 일반적인 권장 방식이다.
배열이나 객체를 반환할 때는 참조(reference)가 바뀌면 리렌더가 발생할 수 있다.
이 경우 shallow 비교를 사용하면 불필요한 리렌더를 줄일 수 있다.

"Zustand는 필요한 상태만 selector로 구독하자. 전체 구독은 편하지만 리렌더가 늘어난다."
