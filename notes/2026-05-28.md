주문서 수량은 사용자가 +/- 버튼을 연속으로 조작하는 고빈도 편집 상태였습니다. 초기에는 서버와 클라이언트가 동시에 수량 상태를 관리하면서 SSOT가 모호해졌고, 그 결과 응답 순서에 따라 화면이 덮어써지는 race condition과 과도한 mutation 호출 문제가 발생했습니다. 이를 해결하기 위해 편집 중에는 Zustand를 SSOT로 두고, 제출 시점에만 서버와 동기화하는 방식으로 변경했습니다.


## 문제

주문서 수량은 사용자가 +/-를 연속으로 조작하는 고빈도 편집 상태였다.

초기에는 서버 draft를 실시간으로 동기화하려 했지만
응답 지연과 중복 요청 때문에 UX가 좋지 않았다.

---

## 시도 1. 클릭마다 서버 PATCH

- 서버 상태를 항상 최신으로 유지
- 네트워크 왕복마다 화면 반응
- 연타 UX가 나쁨

결론:
편집 UX에 적합하지 않음

---

## 시도 2. Optimistic Update

- UI 먼저 변경
- 실패 시 rollback

문제:
- mutation이 겹치며 race condition 발생
- isPending 잠금 필요
- 응답이 다시 상태를 덮어씀

결론:
연속 입력 환경에 부적합

---

## 시도 3. Debounce

- API 호출 감소
- 스테퍼 잠금 제거

문제:
- 로컬 상태와 서버 상태가 동시에 존재
- 응답 시점에 따라 숫자가 다시 변경됨

결론:
API 수는 줄였지만 상태 충돌은 해결하지 못함

---

## 최종 선택

편집 중:
- Zustand + persist를 단일 SSOT로 사용

제출 시:
- syncDraftToServer로 서버와 동기화

결과:
- 즉시 반응
- race condition 제거
- 과도한 mutation 제거

트레이드오프:
- 멀티 탭·멀티 디바이스 동시 편집은 고려하지 않음

---

## 배운 점

문제의 본질은 React Query가 아니라
'누가 상태를 소유하는가(SSOT)' 와
'언제 서버와 동기화할 것인가' 였다.
고빈도 편집 화면에서는
실시간 서버 동기화보다
클라이언트 SSOT + 경계 시점 flush가 더 적합했다.
