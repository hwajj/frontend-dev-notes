주문서 수량은 사용자가 +/- 버튼을 연속으로 조작하는 고빈도 편집 상태였습니다. 초기에는 서버와 클라이언트가 동시에 수량 상태를 관리하면서 SSOT가 모호해졌고, 그 결과 응답 순서에 따라 화면이 덮어써지는(중첩된 mutation의 응답 순서에 따라 최신 수량이 이전 응답으로 덮어써질 수 있는) race condition과 과도한 mutation 호출 문제가 발생했습니다. 이를 해결하기 위해 편집 중에는 Zustand를 SSOT로 두고, 제출 시점에만 서버와 동기화하는 방식으로 변경했습니다.

## 문제

주문서 수량은 사용자가 +/-를 연속으로 조작하는 고빈도 편집 상태였다.

초기에는 수량을 변경할 때마다 서버 draft에 PATCH하여 클라이언트와 서버의 수량을 실시간으로 맞추려 했다.
하지만 응답 지연과 중복 요청으로 연속적인 수량 변경 UX가 좋지 않았다.

---

## 시도 1. 클릭마다 서버 PATCH

- PATCH 요청 후 서버 응답을 받아야 다음 상태가 반영됨
- 네트워크 왕복 시간에 따라 UI 반응이 느려짐
- 연속 클릭 시 요청이 여러 개 발생

결론:
편집 UX에 적합하지 않음

---

## 시도 2. Optimistic Update

- UI 먼저 변경
- 실패 시 rollback

문제:

- mutation이 겹치며 race condition 발생
- mutation 중 중복 요청을 막기 위해 isPending으로 스테퍼를 잠그는 방식도 고려함
- 하지만 네트워크가 느리면 사용자가 연속 입력하기 어려움
- 중첩 mutation이 발생하면 응답 순서에 따라 상태가 덮어써질 수 있음

결론:
연속 입력 환경에 부적합

---

## 시도 3. Debounce

- API 호출 감소
- 스테퍼 잠금 제거

문제:

- 로컬 상태와 서버 draft가 동시에 존재
- Debounce는 API 호출 시점만 늦출 뿐, 어느 쪽을 수량의 기준으로 볼지는 해결하지 못함
- 주문서 초기 hydration 과정에서 서버 draft가 로컬 편집 상태를 덮어쓸 가능성이 있음

결론:
API 수는 줄였지만 상태 충돌은 해결하지 못함

---

## 최종 선택

주문서 진입:

- Zustand에 기존 편집 상태가 있으면 로컬 상태 유지
- 로컬 데이터가 없을 때만 서버 draft 조회

편집 중:

- Zustand를 SSOT로 사용
- persist를 통해 새로고침 후에도 편집 상태 유지

제출 시:

- syncDraftToServer로 서버와 동기화

결과:

- 수량 변경 즉시 UI 반영
- 수량 편집 과정에서의 mutation race condition 제거
- +/- 조작마다 발생하던 mutation 제거
- 서버 동기화를 주문 제출 시점으로 한정

트레이드오프:

- 멀티 탭·멀티 디바이스 동시 편집은 고려하지 않음
  서버에서 수량 변경이 발생하더라도 편집 중인 로컬 상태를 우선함

## 배운 점

문제의 본질은 React Query가 아니라
'누가 상태를 소유하는가(SSOT)' 와
'언제 서버와 동기화할 것인가' 였다.
고빈도 편집 화면에서는 모든 변경을 실시간으로 서버에 반영하기보다, 클라이언트에서 편집 상태를 일관되게 관리하고 서버 동기화는 확정 시점에 수행하는 구조가 더 적합했다.

### 1. 서버에 저장된다고 해서 매번 서버에 요청할 필요는 없다

데이터의 **최종 정합성**과 **UI 편집의 즉각적인 반응**은 별개의 문제다.

### 2. Optimistic Update와 Debounce는 만능 해결책이 아니다

- Optimistic Update → UI를 먼저 변경
- Debounce → 요청을 늦춰서 모음
- SSOT → 데이터의 기준을 결정
  각각 해결하는 문제가 다르다.

### 3. 먼저 SSOT를 정해야 한다

같은 값을 로컬·서버·응답에서 동시에 관리하면 동기화 로직이 복잡해진다.
이번 주문서에서는:

> **편집 중에는 Zustand가 SSOT이고, 제출 시 서버와 동기화한다.**  
> 라는 규칙으로 단순화했다.
