# debounce vs throttle

> 작성일: 2026-06-30
> 맥락: 검색창·스크롤·실시간 알림처럼 **짧은 시간에 같은 일이 여러 번** 일어날 때, API·렌더·계산을 매번 할지 한 번으로 묶을지 고민할 때
> 본문 주제: debounce vs throttle — 정의·비교·선택 조건
> 관점: 짧은 시간에 같은 갱신을 몇 번 요청할 것인가
> 범위: 로컬 학습 노트 — Git 미공유, 팀 공유 문서에서 참조하지 않음

## 이 글의 질문

- 입력할 때마다 API를 치면 느린데, **언제 호출을 미루면** 되나?
- 스크롤·리사이즈마다 레이아웃을 다시 그리면 버벅이는데, **매 이벤트 vs 일정 간격** 중 뭐가 맞나?
- WebSocket 알림이 0.1초에 세 번 오면 GET도 세 번 가야 하나?

## 핵심 정리 (결론부터)

| 기법 | 동작 한 줄 | 대표 용도 | 놓치는 것 |
|------|-----------|----------|----------|
| **debounce** | 멈출 때까지 기다렸다가 **마지막(또는 첫+마지막) 한 번** 실행 | 검색 자동완성, 폼 검증, **연속 알림 후 API 1번** | 중간 상태는 반영 안 됨 |
| **throttle** | 정해진 간격마다 **최대 한 번** 실행 (중간은 건너뜀) | 스크롤 위치 표시, 드래그 중 좌표, 진행률 바 | “멈춘 뒤 한 번”이 아니라 **주기적 샘플** |
| **아무 것도 안 함** | 이벤트마다 즉시 실행 | 클릭 1회, 드물게 오는 이벤트 | 폭주 시 서버·UI 부하 |

한 줄 결론: **“끝난 뒤 한 번이면 된다” → debounce**, **“진행 중에도 가끔은 보여줘야 한다” → throttle**.

## 배경 지식 (짧게만)

- **이벤트**: 브라우저·OS가 “입력됐다”, “창 크기 바뀌었다”, “소켓 메시지 왔다”고 앱에 알리는 신호.
- **콜백**: 그 신호를 받아 실행하는 함수 (API 호출, `setState`, DOM 측정 등).
- **비용이 큰 작업**: 네트워크 요청, 무거운 필터·정렬, 레이아웃 재계산 — **횟수를 줄이는 것**이 체감 성능에 직결된다.

## 한눈에

### debounce — “타이핑 멈춘 뒤 300ms 뒤에 검색”

```
입력: a → ab → abc → (멈춤)
API:  ×    ×     ×      ✓ GET /search?q=abc  (한 번)
```

### throttle — “스크롤하는 동안 100ms마다 위치만 갱신”

```
스크롤 이벤트: |||||||||||||||||| (많음)
UI 갱신:       |    |    |    |     (간격마다 최대 1번)
```

### 실시간 알림 + GET (debounce에 가까운 패턴)

```
WS: task_changed → status_changed → new_message  (0.08초 안에 연속)
GET: (대기) → (대기) → ✓ GET /session  (한 번)
```

## 용어 (이 글에서만)

| 용어 | 한 줄 뜻 |
|------|----------|
| debounce | 연속 호출을 **지연·합쳐서** 실행 횟수를 줄이는 기법 |
| throttle | 일정 **시간 창** 안에서 실행 횟수에 **상한**을 두는 기법 |
| leading / trailing | debounce에서 **첫 호출을 즉시** 할지, **마지막만** 할지 |
| 폭주(burst) | 짧은 시간에 같은 종류 이벤트가 많이 몰리는 상황 |

## 관점

“디바운스 라이브러리를 몰라서”가 아니라 **같은 일을 몇 번 할지** 문제다. 먼저 묻는다: **중간 결과가 필요한가**, **마지막 상태만 맞으면 되는가**, **서버·DB에 부담이 가는가**. 답이 “마지막만 맞으면 된다”면 debounce 후보고, “움직이는 동안에도 주기적으로 보여야 한다”면 throttle이다. ms 숫자(80, 300)는 그다음이다.

## 한 줄 요약

연속 이벤트는 그대로 두지 말고, **debounce(끝난 뒤 한 번)** 와 **throttle(간격마다 한 번)** 중 목적에 맞게 고른다.

## 함정 한 가지

**debounce와 throttle을 같은 문제에 동시에 쓰거나**, “느리니까 debounce”만 말하고 **중간 프레임이 필요한 UI**에 붙이면 화면이 끊겨 보인다. 스크롤 위치 고정 헤더·캔버스 드래그는 throttle(또는 `requestAnimationFrame`) 쪽이 맞는 경우가 많다.

## 왜 이렇게인가

### debounce가 하는 일

호출이 올 때마다 **타이머를 리셋**한다. 일정 시간 동안 추가 호출이 없으면 **한 번** 실행한다. 검색창은 사용자가 `react`를 치는 동안 `r`, `re`, `rea`…마다 API를 부르면 낭비이므로, **입력이 잠잠해진 뒤** 최종 문자열로 한 번 조회하는 패턴이 자연스럽다.

변형:

- **trailing only** (가장 흔함): 마지막 입력 후 한 번
- **leading + trailing**: 첫 입력은 즉시, 이후 연속은 마지막에 한 번 더 (더블클릭 방지·즉각 피드백이 필요할 때)

### throttle이 하는 일

“지금부터 100ms 동안은 더 실행하지 않음”처럼 **고정 간격**으로 문을 연다. 스크롤은 이벤트가 초당 수십 번 와도, 사용자 눈에는 **대략 10fps만 갱신**해도 충분한 경우가 많다. 중간 스크롤 위치를 전부 반영할 필요가 없다.

### 비교 표

| 질문 | debounce | throttle |
|------|----------|----------|
| 사용자가 멈춘 뒤 결과만 맞으면 되나? | ✅ | △ |
| 진행 중에도 주기적으로 갱신해야 하나? | △ | ✅ |
| 서버에 “최종 상태” 한 번만내면 되나? | ✅ | △ |
| 애니메이션·스크롤 따라가기 | △ | ✅ |

### 다른 대안

- **`requestAnimationFrame`**: 화면 주사율에 맞춰 DOM/캔버스 갱신 (스크롤·리사이즈 시각 효과)
- **배치·큐**: 서버 쪽에서 짧은 창 안 요청을 합침 (클라이언트 debounce와 짝)
- **아예 설계 변경**: 폴링 간격 늘리기, WS 페이로드에 스냅샷 포함 (별도 동기화 패턴)

## 참고 코드

일반적으로 `setTimeout` / `clearTimeout`으로 trailing debounce를 직접 구현한다. “연속 이벤트를 한 번의 GET으로 합친다”는 주석과 함께, 타이머를 리셋한 뒤 짧은 지연 후 콜백을 호출하는 형태가 흔하다.

## 이 레포에서는

| 상황 | 선택 | 이유 |
|------|------|------|
| 진단 WebSocket에서 `status_changed`·`new_message` 연속 수신 | trailing debounce (~80ms) 후 `GET /sessions/:id` | `task_changed` 직후 `status_changed`가 붙어도 **스냅샷 조회 1번**으로 합침 |
| 검색 자동완성(일반 패턴) | debounce 200~400ms | 타이핑 중간 결과는 불필요 |
| 채팅 입력 스크롤 따라가기 | throttle 또는 rAF | “멈춘 뒤”가 아니라 **스크롤 중 위치** 갱신 |

80ms는 “원론”이 아니라 **이벤트가 겹치는 시간대**를 한 번의 GET으로 묶기 위한 구현값이다. 환경에 따라 50~150ms로 조정한다.

## 더 볼 것 (선택)

- lodash `debounce` / `throttle` 옵션 (`leading`, `maxWait`)
- React 18 `useDeferredValue` — 급하지 않은 UI 갱신 미루기 (검색 결과 표시 등)
- 서버 rate limit과 클라이언트 debounce의 역할 분담
