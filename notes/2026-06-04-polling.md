# Polling — 새로고침 없이 알림이 뜨는 이유

> 작성일: 2026-06-04
> 맥락: 물류에서 주문 상태를 변경했는데, 요양원 화면에서 F5 없이 알림 토스트가 나타났다. 처음에는 WebSocket으로 구현된 줄 알았지만 실제 코드를 보니 Polling 방식이었다.

## 이 글의 질문

- 새로고침 없이 알림이 뜨는 건 어떻게 가능한가?
- Polling은 무엇인가?
- WebSocket과 무슨 차이가 있나?
- 왜 알림은 Polling을 쓰고 채팅은 WebSocket을 쓰는가?

## 핵심 (먼저 읽기)

| 방식      | 누가 먼저 요청?              | 실시간성           | 구현 난이도 |
| --------- | ---------------------------- | ------------------ | ----------- |
| 일반 HTTP | 클라이언트                   | 없음               | 쉬움        |
| Polling   | 클라이언트가 주기적으로 요청 | 수 초~수십 초 지연 | 쉬움        |
| SSE       | 서버 → 클라이언트            | 거의 실시간        | 중간        |
| WebSocket | 양방향                       | 실시간             | 어려움      |

현재 프로젝트:

```ts
refetchInterval: 30000;
```

즉,

```text
30초마다

GET /api/notifications
```

를 호출하는 Polling 방식이다.

WebSocket은 사용하지 않는다.

## 전제 (30초)

### HTTP

브라우저가 서버에게 요청을 보내고 응답을 받는 방식.

```text
브라우저
   │
   ├── GET /orders
   │
   ◀── 주문 목록
```

### Polling

클라이언트가 일정 시간마다 같은 API를 반복 호출하는 방식.

```text
30초마다

GET /notifications
```

### WebSocket

클라이언트와 서버가 연결을 유지한 채 서로 데이터를 주고받는 방식.

## 한눈에

### 일반 조회

```text
사용자
   │
F5
   │
GET /notifications
   │
응답
```

### Polling

```text
브라우저
   │
30초
   │
GET /notifications
   │
응답
   │
30초
   │
GET /notifications
```

### WebSocket

```text
브라우저 ───────── 서버
      연결 유지

서버 → 새 알림 발생
서버 → 즉시 전송
```

## 용어

| 용어            | 뜻                                             |
| --------------- | ---------------------------------------------- |
| Polling         | 일정 간격으로 서버에 변경 여부를 확인하는 방식 |
| Short Polling   | 매 N초마다 요청                                |
| Long Polling    | 응답을 오래 붙잡고 있다가 변경 시 응답         |
| SSE             | 서버 → 클라이언트 단방향 Push                  |
| WebSocket       | 양방향 실시간 통신                             |
| refetchInterval | TanStack Query의 폴링 주기 설정                |

## 한 줄 요약

Polling은 서버가 알려주는 것이 아니라, 클라이언트가 주기적으로 "새 거 있어?"라고 물어보는 방식이다.

## 현재 프로젝트는 어떻게 동작하나

### 1. 물류가 상태 변경

예:

```text
배송준비중
→ 배송중
```

### 2. 서버가 알림 저장

```sql
INSERT INTO notifications
```

notifications 테이블에 새 레코드 생성.

### 3. 요양원 브라우저가 조회

```text
30초마다

GET /api/notifications
```

### 4. 새 알림 발견

```ts
toast("info", latest.message);
```

토스트 출력.

그래서 사용자는

```text
새로고침 안 했는데 알림이 떴네?
```

라고 느끼게 된다.

## 왜 Polling을 사용하는가

### 장점

구현이 단순하다.

기존 REST API만 있으면 된다.

```text
GET /notifications
```

하나만 만들면 된다.

인증·재연결·커넥션 관리도 거의 필요 없다.

### 단점

실시간이 아니다.

```text
30초 Polling
```

이면

```text
0~30초
```

사이의 지연이 발생할 수 있다.

또한 변경이 없어도 계속 요청한다.

## 왜 모든 기능을 Polling으로 만들지 않을까

예를 들어 채팅을 생각해보자.

### Polling

```text
30초마다

새 메시지 있어?
```

30초 뒤에 답장이 보인다.

채팅이 사실상 불가능하다.

### WebSocket

```text
메시지 도착

즉시 전송
```

실시간 대화 가능.

따라서:

| 기능            | 적합한 방식 |
| --------------- | ----------- |
| 알림            | Polling     |
| 관리자 대시보드 | Polling     |
| 주문 현황       | Polling     |
| 채팅            | WebSocket   |
| 실시간 게임     | WebSocket   |
| 협업 편집       | WebSocket   |

## 이 레포에서는

### notificationPollingQuery

```ts
refetchInterval: 30_000;
```

30초마다 알림 API 조회.

### useNotificationPolling

```ts
if (latest.id !== lastSeenIdRef.current) {
  toast(...)
}
```

새 알림 감지 시 토스트 출력.

### notifyNursingHomeUsers

```ts
db.insert(notifications);
```

알림 DB 저장.

즉,

```text
상태 변경
  ↓
notifications INSERT
  ↓
30초 Polling
  ↓
새 알림 감지
  ↓
토스트 출력
```

구조다.

## 면접 포인트

"새로고침 없이 알림을 구현해 본 경험이 있나요?"

답변 예시:

현재 프로젝트에서는 WebSocket 대신 Polling 방식을 사용했습니다. 상태 변경 시 notifications 테이블에 알림을 저장하고, 클라이언트는 TanStack Query의 refetchInterval을 통해 30초마다 알림 API를 조회합니다. 새 알림이 감지되면 토스트와 unreadCount를 갱신합니다. 알림은 수 초의 지연이 허용되기 때문에 구현 복잡도가 낮은 Polling을 선택했습니다.
