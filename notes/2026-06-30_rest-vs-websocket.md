# REST vs WebSocket

> 작성일: 2026-06-30
> 맥락: 채팅·진단·주문 추적처럼 “지금 상태”가 바뀌는 기능을 만들 때, HTTP만 쓸지 WebSocket을 열지, 둘을 섞을지 고민할 때
> 본문 주제: REST(HTTP 요청-응답) vs WebSocket — 연결 모델·역할·적합한 작업
> 관점: 이건 한 번 답이면 되나, 진행 중 갱신이 필요한가
> 범위: 로컬 학습 노트 — Git 미공유, 팀 공유 문서에서 참조하지 않음

## 이 글의 질문

- “실시간 챗봇”이면 전부 WebSocket이어야 하나?
- GET 한 번으로 끝나는 API와, 연결을 계속 유지하는 소켓의 **차이**는?
- 서버가 작업 중일 때 클라이언트는 **폴링·SSE·WS** 중 뭘 써야 하나?

## 핵심 정리 (결론부터)

| | HTTP (REST) | WebSocket |
|---|-------------|-----------|
| **연결** | 요청마다 연결 열고 닫기 (또는 keep-alive 재사용) | **한 번 핸드셰이크 후 지속** |
| **누가 먼저 말하나** | 항상 **클라이언트** | **서버도** 먼저 push 가능 |
| **한 번에 주고받는 단위** | 요청 1 ↔ 응답 1 | **양방향 프레임** (텍스트·바이너리) |
| **잘 맞는 일** | CRUD, 제출, **스냅샷 조회** | 알림, 진행률, **채팅 스트림**, 협업 |
| **부담** | 짧은 트랜잭션에 유리 | 연결 수·재연결·방화벽·상태 관리 |

한 줄 결론: **“지금 전체 상태 알려줘”는 HTTP**, **“바뀌면 바로 알려줘”는 WebSocket(또는 SSE)** — 많은 제품이 **둘을 같이** 쓴다.

## 배경 지식 (짧게만)

- **HTTP**: 브라우저가 서버에 “이 URL로 이 메서드로” 요청하고, 서버가 **상태 코드 + 본문**으로 답하는 규약.
- **REST**: HTTP를 **리소스(URL) + 메서드(GET/POST/…)** 로 쓰는 설계 스타일. “REST API”는 보통 JSON over HTTP를 뜻한다.
- **WebSocket**: HTTP로 업그레이드한 뒤, **TCP 위에 양방향 채널**을 유지한다.

## 한눈에

### REST만 — 폴링

```
클라이언트: GET /job/1  → processing
 (2초 후)
클라이언트: GET /job/1  → processing
 (2초 후)
클라이언트: GET /job/1  → done
```

서버는 조용히 있어도 클라이언트가 **주기적으로 물어본다**. 구현은 단순하지만 **빈 요청**이 많다.

### WebSocket — 서버 push

```
클라이언트: WS 연결 /job/1/stream
서버: { "status": "processing" }
서버: { "status": "done" }
```

바뀔 때만 **서버가 보낸다**. 연결은 **계속 열려** 있다.

### 하이브리드 (실무에서 흔함)

```
클라이언트: POST /messages        ← 메시지 보내기 (REST)
클라이언트: WS 연결               ← "new_message" 알림만
클라이언트: GET /sessions/:id     ← 화면 그릴 전체 스냅샷 (REST)
```

## 용어 (이 글에서만)

| 용어 | 한 줄 뜻 |
|------|----------|
| 요청-응답 | 클라이언트가 먼저 요청하고 서버가 한 번 응답 |
| 지속 연결 | 한 TCP(또는 WS) 세션을 오래 유지 |
| push | 서버가 먼저 클라이언트로 데이터 전송 |
| 폴링 | 클라이언트가 일정 간격으로 같은 API 반복 호출 |
| SSE | 서버→클라이언트 **단방향** 스트림 (HTTP 기반) |
| 핸드셰이크 | WS 시작 전 HTTP Upgrade로 “채널 바꿀게” 합의 |

---

## 관점

“소켓 썼으니 실시간이다”가 아니라 **무엇을 실시간으로 할지**부터 정한다. 메시지 **본문 전체**를 스트리밍할지, **바뀌었다는 신호**만 줄지에 따라 REST 비중이 달라진다. 연결은 비용이다 — **알림만 필요하면 WS + GET 스냅샷**이 흔하고, **한 번의 질문·한 번의 답**이면 REST만으로 충분하다.

## 한 줄 요약

REST는 **질문할 때마다 스냅샷**을 받는 전화 한 통이고, WebSocket은 **문 열어두고 서버가 먼저 말할 수 있는** 채널이다.

## 함정 한 가지

**모든 것을 WebSocket에 실으면** 클라이언트·서버 모두 “WS에 붙은 JSON”과 “REST JSON” **두 벌 진실**을 맞춰야 한다. 캐시·버전·재연결 시 유실까지 고려하면, **알림은 WS, 화면 데이터는 GET** 으로 나누는 팀이 많다.

## 언제 무엇을 쓰나

| 필요 | 1순위 후보 | 이유 |
|------|-----------|------|
| 폼 제출, 결제, 파일 업로드 | REST POST/PUT | 멱등·재시도·표준 상태 코드 |
| 목록·상세 **한 시점** 조회 | REST GET | 캐시·CDN·도구 지원 좋음 |
| 서버 작업 **완료만** 알면 됨 | 폴링 또는 SSE/WS | 빈도 낮으면 폴링도 OK |
| 채팅 **글자 단위** 스트리밍 | WS 또는 SSE | 서버→클라 push |
| “상태 바뀜”만 알림 | WS + REST GET | 페이로드 작게, SSOT는 GET |

### REST에 가까운 선택

- 질문에 대한 답이 **한 번에 끝남**
- 클라이언트가 **필요할 때만** 서버를 치면 됨
- 중간 진행을 **안 보여줘도** 됨

### WebSocket에 가까운 선택

- 서버가 **먼저** 알려줘야 함
- 이벤트가 **잦고** 폴링이 낭비임
- 양방향 **저지연** (게임, 협업 커서 등)

### SSE vs WebSocket (짧게)

- **SSE**: HTTP, 서버→클라 **단방향**, 재연결·텍스트에 단순
- **WebSocket**: **양방향**, 바이너리·프로토콜 자유도 큼, 인프라·방화벽 이슈를 한 번 더 봄

## 왜 이렇게인가

HTTP는 원래 **문서 요청** 모델이다. “연결 유지 비용”을 줄이려 요청마다 끊는 쪽이 기본에 가깝다(keep-alive는 최적화). 그래서 **클라이언트가 원할 때 물어보는** API에 잘 맞는다.

WebSocket은 **긴 대화** 모델이다. 채팅·주식 틱·진행률처럼 **시간에 따라 서버가 말할 일이 생기면** 매번 HTTP 헤더를 새로 치는 것보다 한 채널이 낫다.

다만 **채널을 연다**는 것은 서버에 **동시 연결 상태**를 둔다는 뜻이다. 스케일·재연결·로드밸런서 sticky session·하트비트(ping/pong)가 따라온다.

## 연결 유지와 하트비트

중간 프록시·방화벽은 **조용한 연결**을 끊을 수 있다. 그래서 WS에서는 주기적으로 **ping/pong** 또는 작은 메시지로 “살아 있음”을 보낸다. 이건 **전송 방식의 운영 디테일**이지 비즈니스 이벤트가 아니다.

## 참고 코드

브라우저 WebSocket은 대략 다음 순서다.

1. `new WebSocket(url)` — HTTP Upgrade
2. `onopen` — 연결 성공
3. `onmessage` — 서버 프레임 수신
4. `send()` — 클라이언트 전송
5. `close()` / 탭 닫기 — 정리

JSON 비즈니스 메시지와 평문 `ping`/`pong`을 **같은 채널**에서 섞는 구현도 흔하다. 파싱 계층에서 구분한다.

## 이 레포에서는

| 역할 | 방식 |
|------|------|
| 사용자 메시지 전송 | REST API |
| 진단 세션 **상태·메시지 목록** | REST `GET /sessions/:id` |
| 서버 처리 중 **변경 알림** | WebSocket (`task_changed`, `status_changed`, `new_message`) |
| WS 수신 후 화면 갱신 | 이벤트 타입에 따라 **GET 재조회** (본문은 WS에 안 실음) |
| 연결 직후 | 한 번 GET — **누락된 push** 보정 |

즉 “챗봇 = 전부 소켓”이 아니라, **대화 제출·스냅샷은 REST**, **긴 작업의 변화 신호는 WS**로 나뉜다. 연속 알림 뒤 GET은 debounce로 묶는다(별도 노트).
