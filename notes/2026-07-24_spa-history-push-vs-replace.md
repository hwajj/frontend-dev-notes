# SPA history — push vs replace

> 작성일: 2026-07-24  
> 맥락: 상세 → 수정 화면 → 다시 상세로 돌아온 뒤, 뒤로가기를 누르면 수정 화면과 상세를 오가며 루프처럼 느껴질 때  
> 본문 주제: SPA history 스택에서 `navigate`(push)와 `replace`의 차이 · “돌아올 URL”을 스택에 어떻게 올릴지  
> 관점: 돌아올 URL을 push하면 왜 뒤로가기가 루프가 되나  
> 범위: 로컬 학습 노트 — Git 미공유, 팀 공유 문서에서 참조하지 않음

## 이 글의 질문

- 브라우저 뒤로가기와 앱 헤더의 “이전”이 같은 스택을 쓰나?
- “이 화면에서 저 URL로 가라”고 `navigate(url)` 하면, 뒤로가기 한 번에 어디로 가나?
- 편집을 마치고 원래 화면으로 돌아갈 때 **스택을 늘려야** 하나, **지금 칸을 바꿔야** 하나?

## 핵심 정리 (결론부터)

| 방식 | history에 하는 일 | 뒤로가기 한 번 | 편집→상세 복귀에 맞나 |
|------|-------------------|----------------|------------------------|
| A. push (`navigate(url)`) | **새 칸**을 위에 쌓음 | 방금 떠나온 화면(수정 페이지) | ❌ 상세↔수정이 반복되기 쉬움 |
| B. replace (`navigate(url, { replace: true })`) | **지금 칸을** url로 교체 | 수정 이전의 진짜 이전(목록 등) | ✅ 왕복이 스택에 안 남음 |
| C. `navigate(-1)` | 스택을 **한 칸 pop** | 직전에 push된 주소 | △ URL·hash를 정확히 맞추기 어렵거나, 스택이 꼬이면 실패 |

한 줄: **“돌아올 주소”를 다시 push하면, 뒤로가기의 ‘이전’이 그 수정 화면이 된다.** 편집 복귀는 대개 **replace**다.

## 배경 지식 (짧게만)

- **History 스택**: 탭이 “방문한 주소”를 쌓아 둔 목록. 뒤로가기 = 한 칸 아래로 이동.
- **SPA(Single Page Application)**: 전체 문서를 새로 받기보다, JS가 주소만 바꾸고 화면을 갈아끼움. React Router의 `navigate`도 이 스택을 조작한다.
- **push**: 스택 길이가 +1. 주소창은 새 URL, “뒤로”는 직전 URL.
- **replace**: 스택 길이는 그대로. 지금 칸의 URL만 바뀜. “뒤로”는 **그 전** 칸.
- **returnUrl**: “나중에 여기로 돌아와”라고 쿼리에 실어 보내는 **복귀 목적지** 문자열. 그 자체는 push/replace를 정하지 않는다 — **어떻게 navigate하느냐**가 스택을 정한다.

## 한눈에

### 경로 A — 복귀를 push (루프가 나기 쉬운 쪽)

```
[목록] → push → [상세] → push → [수정]
                              │
                    navigate(returnUrl)  ← push (기본)
                              ▼
                         [상세]  (스택에 수정이 그대로 남음)
                              │
                         뒤로가기
                              ▼
                         [수정]  ← 사용자가 기대한 “목록/바깥”이 아님
                              │
                         뒤로가기(또는 헤더가 또 push)
                              ▼
                         [상세] … 반복처럼 보임
```

### 경로 B — 복귀를 replace (왕복을 스택에서 지움)

```
[목록] → push → [상세] → push → [수정]
                              │
              navigate(returnUrl, { replace: true })
                              ▼
                         [상세]  (수정 칸이 상세로 **교체**)
                              │
                         뒤로가기
                              ▼
                         [목록]  ← 수정 화면은 이미 스택에 없음
```

## 용어 (이 글에서만)

| 용어 | 한 줄 뜻 |
|------|----------|
| history 스택 | 탭의 방문 기록 목록 |
| push | 새 기록을 위에 쌓기 |
| replace | 현재 기록을 다른 URL로 바꾸기 |
| pop / `navigate(-1)` | 한 칸 뒤로(스택에서 내려가기) |
| returnUrl | “편집 후 돌아갈 주소”를 담은 쿼리 값 |
| SPA | 주소 변경을 JS가 처리하는 한 페이지 앱 |

---

## 관점

흔한 착각은 “뒤로가기가 이상하면 헤더 핸들러 버그” 또는 “브라우저 제스처 문제”로 보는 것이다.  
실제로는 **편집을 끝낸 뒤 상세로 ‘가는’ 방식이, 스택에 수정 화면을 남겼는지**가 먼저다.  
`returnUrl`을 아는 것과, 그 URL로 **push할지 replace할지**는 다른 결정이다.  
판단 축은 셋이다. **누가**(사용자 뒤로가기 vs 앱 버튼) · **언제**(편집 진입 vs 편집 종료) · **얼마나**(스택에 왕복을 남길지).  
라이브러리 API 이름보다 “이 화면이 히스토리에 **남아야 하는 방문**인가”를 먼저 묻는다.

## 한 줄 요약

편집 화면에서 원래 화면으로 복귀할 때는 대개 **push가 아니라 replace**로, 수정 칸을 목적지로 교체한다.

## 함정 한 가지

뒤로가기(헤더)만 `replace`하고 **적용(확인) 버튼**은 기본 `navigate(url)`로 두면, “적용으로 돌아온 뒤”에만 루프가 다시 난다. **복귀하는 모든 경로**에 같은 스택 정책을 써야 한다.

---

## 왜 이렇게인가

### 1. 언제 발생하나 (조건)

다음이 **동시에** 있을 때 루프·중복 뒤로가기가 잘 난다.

| 조건 | 설명 |
|------|------|
| SPA + 클라이언트 라우팅 | `navigate`가 history를 직접 조작 |
| 상세 → 수정이 **push** | 수정이 스택 위에 쌓임 |
| 수정 → 상세이 **또 push** | 상세가 한 번 더 쌓이고, 그 아래에는 수정이 남음 |
| 사용자가 “바깥으로” 기대 | 두 번째 뒤로가기가 목록이어야 하는데 수정으로 감 |

브라우저 자체 버그가 아니라, **의도한 ‘이전’과 스택의 ‘이전’이 어긋난 상태**다.

### 2. 왜 push / replace가 나뉘어 있나 (목적)

웹에서 “링크를 따라간다”는 보통 **새 방문(push)** 이다. 뒤로가기로 되돌아갈 수 있어야 한다.  
반면 “같은 일을 마친 뒤 URL만 정리한다”, “리다이렉트로 중간 주소를 남기지 않는다”는 **replace**에 가깝다.  
로그인 후 `/login`을 홈으로 바꾸는 것, 마법사 중간 스텝을 확정 화면으로 덮는 것이 전형적이다.

편집 UX도 후자에 가깝다. 사용자는 “수정 화면을 **거친 방문**”으로 남기기보다, “상세를 고치다 잠깐 연 도구”로 느끼는 경우가 많다. 도구를 닫으면 스택에서도 지우는 편이 기대와 맞다.

### 3. 도구·경로 비교

아래는 **같은 목적지 URL**이라도 스택 결과가 다르다는 점을 보여 준다.  
예: 상세 Origin `http://localhost:3000`, 경로만 단순화.

| 시나리오 | 하는 일 | 페이지 Origin | Request URL(주소창) | 스택 길이 | 다음 뒤로가기 |
|----------|---------|---------------|---------------------|-----------|----------------|
| A — 복귀 push | `navigate('/detail/1')` | `http://localhost:3000` | `http://localhost:3000/detail/1` | +1 | 수정 페이지 |
| B — 복귀 replace | `navigate('/detail/1', { replace: true })` | 동일 | 동일 | 0 변화 | 목록 등 그전 칸 |
| C — pop | `navigate(-1)` | 동일 | 직전 칸 URL | −1 | 그전전 칸 |

HTTP 요청이 없어도(클라이언트 라우팅만으로도) **history API 동작은 같다.**  
“주소는 같아 보이는데 뒤로가기가 다르다”면 Network 탭이 아니라 **Application/history에 무엇이 쌓였는지**를 보면 된다.

### 4. replace를 안 한 경우 (증상이 보이는 구성)

```
상세  --push--> 수정  --push(returnUrl)--> 상세'
```

스택 예:

1. `/list`  
2. `/detail/1`  
3. `/edit?returnUrl=...`  
4. `/detail/1`  ← 4번이 3번 **위**에 push됨. 3번은 사라지지 않음.

뒤로가기: 4→3(수정) →2(상세) →1(목록).  
사용자는 4→1 또는 4→2→1을 기대하는 경우가 많아, 3이 끼어 있으면 “루프”로 보고한다.

### 5. `navigate(-1)`만으로 부족한 이유

- 복귀 대상에 **hash**(예: `#schedule`)·쿼리(예: `reFlag`)가 있으면, “한 칸 전”이 그 정확한 URL이 아닐 수 있다.
- 중간에 다른 push(모달 라우트, 검색 화면)가 끼면 −1의 의미가 바뀐다.
- 그래서 “돌아갈 주소를 문자열로 들고 다니되(**returnUrl**), 복귀 시에는 **replace로 현재 칸을 그 주소로 덮는다**”는 조합이 흔하다.

### 6. 디버깅 체크리스트

1. 수정 진입 직전·직후·복귀 직후에 주소창 URL을 적는다.  
2. 복귀 코드가 `replace: true`인지 확인한다. **헤더 이전**과 **적용/확인**을 둘 다 본다.  
3. 복귀 후 뒤로가기를 한 번 눌러, 수정 URL이 다시 나오는지 본다. 나오면 아직 push 복귀 경로가 남아 있다.  
4. 앱 헤더가 `navigate(returnUrl)`로 **또 push**하는지, 브라우저 네이티브 뒤로가기와 같은지 구분한다.

## 참고 코드

일반적으로 React Router v6에서 “현재 기록을 교체”하는 호출이다.

```ts
// push (기본) — 스택 +1
navigate('/care/detail/edit/...');

// replace — 현재 칸만 교체
navigate('/care/detail/edit/...', { replace: true });
```

이 레포(간병 care)에서는 편집 모드 복귀가 대략 다음과 같다.

```ts
// 편집 화면에서 이전/적용 후 상세로 복귀할 때
if (returnUrl) {
  navigate(decodeURIComponent(returnUrl), { replace: true });
}
```

`returnUrl`은 상세의 “수정하기”가 만들며, 수정 화면 쿼리로 넘어온다. **만드는 쪽**과 **소비하는 쪽(replace)** 이 한 세트다.

## 이 레포에서는

| 개념 | 이 프로젝트에서의 위치 |
|------|------------------------|
| returnUrl 생성 | 상세의 수정하기 버튼 — 현재 `pathname`+쿼리(+hash)를 문자열로 실어 보냄 |
| 편집 진입 | `/care/newRegist/...?isEdit=true&returnUrl=...` 로 **push** (수정은 새 방문) |
| 편집 종료 | Location / Period / Certificate 등에서 `navigate(decodeURIComponent(returnUrl), { replace: true })` |
| 루프가 났던 이유 | 복귀가 기본 push라 수정 칸이 스택에 남음 + (별 이슈로) 복귀 URL의 쿼리 깨짐이 겹치면 더 헷갈림 |

다른 서비스가 `navigate(-1)` 중심이면 스택이 단순해 “루프”가 안 보일 수 있다. **같은 제품이라도 플로우마다 history 정책이 다르면** 증상도 갈린다.
