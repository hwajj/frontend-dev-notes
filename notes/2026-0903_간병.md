useDetailData는 detailData를 만들지 않습니다. Context에서 이미 만들어진 값을 읽기만 하는 훅입니다. 실제 생성·갱신은 detail.tsx의 CareDetail 컴포넌트에서 이루어집니다.

### 1. useDetailData의 역할

```
const useDetailData = () => {
  return useContext(DetailDataContext);
};
```

DetailDataContext.Provider가 detail.tsx에서 값을 주입합니다.

```
 <DetailDataContext.Provider value={{ detailType, detailData, setDetailData, jobStatus, setJobStatus }}>

```

하위 컴포넌트(bigData.tsx, cagiverList.tsx 등)는 useDetailData()로 { detailType, detailData, setDetailData, jobStatus, setJobStatus }를 받습니다.

### 2. detailData는 어디서 만들어지나

CareDetail에서 useState로 관리됩니다.

const [detailData, setDetailData] = useState<CareType>(fromStoreToCare() as unknown as CareType);
초기값은 Redux store + 등록 폼 slice들을 **fromStoreToCare()**로 합친 CareType 객체입니다.

변환 로직은 useAdaptDetailData 훅에 있습니다.

함수 방향 용도
fromStoreToCare()
Redux store → UI (CareType)
등록/수정 미리보기
fromResponseToCare(res)
API 응답 → UI (CareType)
상세 조회/재등록
fromCareToStore(tr)
UI → Redux store
API 조회 후 store 동기화 3. fromStoreToCare() — 등록/수정 경로
Redux의 여러 slice를 하나의 CareType으로 합칩니다.

detailData는 CareDetail의 로컬 state이지만, 하위 20개 이상 컴포넌트가 필요합니다. props drilling 대신 Context로 { detailData, setDetailData, jobStatus, detailType }를 공유합니다.

정리:

useDetailData() = Context reader
detailData 생성 = fromStoreToCare() 또는 fromResponseToCare()
상태 소유 = detail.tsx의 useState
갱신 = setDetailData (직접 또는 하위 컴포넌트)
특정 필드(예: ptr_certificate_schedule, job_type)의 변환만 더 깊게 보고 싶으면 알려주세요.

detail_type은 어떻게 생기는거야?

detail_type(snake_case) 필드는 이 코드베이스에 없습니다. 말씀하신 건 아마 detailType(camelCase)일 가능성이 큽니다. 이 값은 detailData처럼 API나 fromStoreToCare()로 만들어지지 않고, URL 경로의 :type 파라미터에서 읽어옵니다.

1. detailType은 어디서 오나
   const detailType = (params.type || 'register') as CareDetailType;
   React Router의 useParams().type → detailType으로 매핑됩니다.

가능한 값은 3가지입니다.

값 의미
register
신규 등록 미리보기
edit
기존 공고 수정
view
등록된 공고 상세 조회
라우트 정의:

                  <Route path='detail'>
                    <Route path=':type/:jobId' element={<CareDetail />} />
                    <Route path=':type/:time/:place' element={<CareDetail />} />
                    <Route path=':type/:time/:place/:jobId' element={<CareDetail />} />
                  </Route>

예시 URL:

/care/detail/register/day/hospital/0 → detailType = 'register'
/care/detail/edit/term/home/123 → detailType = 'edit'
/care/detail/view/456 → detailType = 'view' 2. detailData와의 차이
detailType detailData
출처

Redux store 또는 API
생성 시점
navigate() 할 때
fromStoreToCare() / fromResponseToCare()
저장 위치
Context로 전달 (로컬 state 아님)

하위 컴포넌트는 useDetailData()로 { detailType, detailData, ... }를 받습니다.

3.  각 detailType은 누가 URL에 넣나
    view — 공고 상세 보기
    목록에서 "보기" 클릭 시:

              pathname: `/care/detail/view/${job.id}`,

    register — 신규 등록 / 재등록 미리보기
    등록 플로우 마지막: /care/detail/register/day/hospital/0
    재등록: /care/detail/register/...?reFlag=true (reFlag는 query, detailType은 여전히 register)
    const pathname = `/care/detail/register/${job.job_type}/${job.ptr_job_care.request_type}/${job.id}`;
    edit — 기존 공고 수정
    jobId > 0이면 edit, 아니면 register로 분기하는 패턴이 있습니다.

            const detailType = jobId && !jobIdZero ? 'edit' : 'register';
            const detailJobId = jobId && !jobIdZero ? jobId : '0';
            navigate(`/care/detail/${detailType}/${jobType}/${locationType}/${detailJobId}`, { replace: true });

    상세 화면에서 "수정" 진입:

              pathname: `/care/detail/edit/${detailData.job_type}/${detailData.request_type}/${jobId}`,

4.  detailType이 화면 동작을 어떻게 바꾸나
    같은 CareDetail 컴포넌트지만, URL의 detailType에 따라 분기됩니다.

detailType
├── register / edit
│ ├── detailData ← fromStoreToCare() (Redux store 기반)
│ ├── 버튼: "등록하기" / "수정완료"
│ └── API 호출 없음 (store 변경 시 setDetailData 동기화)
│
└── view
├── detailData ← careDetail API → fromResponseToCare()
├── 버튼: 조회 전용 UI
└── jobStatus (지원자, 결제, 그래프 등) API로 채움
