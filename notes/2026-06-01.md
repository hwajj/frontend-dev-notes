웹 서비스는 보통 브라우저가 DB에 직접 접속하지 않고, API 서버가 대신 DB에 질의한다.
API 서버가 DB와 통신하려면 "DB 연결(Connection)"이 필요한데, 이 연결을 매번 새로 만들면 느려서 여러 개를 미리 만들어 재사용한다. 이것이 "연결 풀(Connection Pool)"이다.
Supabase의 pool_size: 15는 "사용자 15명 제한"이 아니라 "동시에 유지 가능한 DB 연결 15개 제한"을 의미한다.
사용자 100명이 접속해도 연결을 효율적으로 재사용하면 문제없지만, 연결이 15개 모두 사용 중이면 새 연결은 거부된다.
개발 환경에서는 dev 서버, DB 관리 툴, 테스트 코드 등이 동시에 연결을 만들어 생각보다 빨리 한도에 도달할 수 있다.
그래서 max clients reached 에러는 대개 SQL 문법 오류가 아니라 "DB 연결이 부족하다"는 신호다.
서버 재시작 후 잠시 정상 동작하는 이유도 기존 연결들이 정리되어 슬롯이 비워지기 때문이다.
실무에서는 연결 수를 줄이거나 Transaction Pool(6543)을 사용해 이런 문제를 완화하는 경우가 많다.

한 문장으로 요약하면:

DB 연결은 서버가 DB와 통화하는 전화선이고, max clients reached는 사용자가 많아서가 아니라 그 전화선이 모두 사용 중이라 더 이상 연결할 수 없다는 뜻이다.


----

Supabase는 DB를 보호하려고 "동시에 열어둘 수 있는 DB 연결 수"를 제한한다.
Session Pool(5432)은 한 번 연결하면 계속 붙잡고 있어서 연결 슬롯이 잘 안 비워진다.
pool_size: 15는 "DB 연결을 동시에 15개까지만 유지 가능"이라는 뜻이다.
여기서 세션(Session)은 로그인 세션이 아니라 "프로그램과 DB 사이의 연결"이다.
개발 서버, DB 관리 툴, 테스트 코드가 각각 연결을 열면 금방 15개가 찰 수 있다.
15개가 모두 사용 중인데 새 연결을 만들려고 하면 max clients reached 오류가 난다.
Transaction Pool(6543)은 쿼리 끝나면 연결을 빨리 반납해서 같은 환경에서도 훨씬 많은 요청을 처리할 수 있다.
그래서 일반적인 API 서버는 보통 Transaction Pool을 쓰고, Session Pool은 연결 상태를 오래 유지해야 하는 특별한 경우에 주로 사용한다.

한 문장으로 요약하면:

"15명까지 접속 가능"이 아니라 "DB 연결 15개까지만 동시에 유지 가능"이고, Session Pool은 그 연결을 오래 잡고 있어서 한도에 빨리 걸린다.
