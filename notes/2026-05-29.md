### CORS와 Vite Proxy
로컬 개발 환경에서는 프론트 서버가 5173, API 서버가 3001이라 브라우저가 3001을 직접 호출하면 CORS 검사가 발생합니다. 그래서 Vite Proxy를 사용했습니다. 브라우저는 5173의 /api만 호출하고, Vite가 내부적으로 3001 서버에 요청을 전달합니다. 브라우저 입장에서는 같은 출처(5173)로 요청한 것으로 보이기 때문에 개발 환경에서 CORS 문제를 신경 쓰지 않고 개발할 수 있었습니다.

브라우저는 보통 DB나 API 서버에 직접 가지 않고, 현재 웹페이지 주소(예: 5173)로 요청을 보낸다.
이 프로젝트는 API 주소를 '/api'로 써서 브라우저가 http://localhost:5173/api/...로 요청하게 만든다.
Vite가 그 요청을 뒤에서 http://localhost:3001/api/...로 대신 전달한다(프록시).
그래서 브라우저 입장에서는 계속 5173만 보고 있어서 CORS 문제가 잘 발생하지 않는다.
반대로 VITE_API_BASE_URL=http://localhost:3001/api를 넣으면 브라우저가 3001에 직접 요청하게 되고, 이때 CORS가 발생할 수 있다.
개발 중 API가 안 되면 CORS보다 먼저 "3001 서버가 켜져 있는지", "서버를 두 번 실행한 건 아닌지" 확인하는 게 중요하다.
npm run dev를 루트에서 실행하면 프론트(5173)와 백엔드(3001)가 같이 켜지므로 보통 이것만 쓰면 된다.

한 문장으로 요약하면:

이 프로젝트는 브라우저가 3001 서버를 직접 호출하지 않고 Vite 프록시가 대신 전달하기 때문에, 평소에는 CORS를 거의 신경 쓰지 않아도 된다.

### SPA의 인증 상태
SPA의 인증 상태는 메모리, 브라우저 저장소, 서버 등 여러 계층에 존재할 수 있다.
UI가 보여주는 로그인 상태와 실제 인증 상태는 서로 다를 수 있다.
로그아웃은 단순한 state 초기화가 아니라 인증 상태를 제거하는 과정이다.
새로고침 후 로그인 유지 기능은 저장된 인증 정보를 이용해 인증 상태를 복원하는 것이다.
인증 관련 문제는 여러 계층의 인증 상태가 서로 불일치할 때 주로 발생한다.
